# Backlog

아직 구현 분석에 착수하지 않은 발견 사항과 보완 작업을 관리한다.

Backlog는 구현 상세 문서가 아니다. 문제의 근거, 수용 여부, 처리 시점, blocking 대상과 현재 상태를 기록하며, 실제 작업을 시작할 때 `docs/specs/`의 분석·설계·구현·검증·적대적 리뷰 파이프라인으로 승격한다.

## 문서 역할

| 위치 | 역할 |
|---|---|
| `docs/backlog/` | 발견됐지만 아직 착수하지 않은 작업과 단계별 삽입 지점 |
| `docs/specs/` | 착수가 확정된 작업의 분석·설계·구현·검증·적대적 리뷰 |
| `docs/worklog/` | 실제 수행 과정과 결과 |
| `docs/worklog/HANDOFF.md` | 현재 상태, 현재 체크포인트와 바로 다음 행동 |

HANDOFF는 backlog 전체를 복사하지 않는다. 현재 단계 전환을 실제로 막는 항목만 ID와 문서 링크로 가리킨다. `Blocks`가 `없음`인 항목은 남아 있어도 다른 작업이나 Tier 진입을 자동으로 막지 않는다.

## 작업 생명주기

```text
발견
→ backlog 등록·근거 대조·판정
→ 처리 시점과 blocking 대상 지정
→ 구현 분석 착수
→ spec 승격
→ 구현·검증·적대적 리뷰
→ worklog 기록
→ backlog 상태와 HANDOFF 갱신
```

상태 값은 다음 의미로 사용한다.

- `PENDING`: 판정됐지만 구현 분석에 착수하지 않음
- `INVESTIGATE`: 안전한 설계에 필요한 증거가 부족함
- `PROMOTED`: 별도 spec에서 분석 또는 구현에 착수함
- `DEFERRED`: 근거를 갖고 이후 단계에 배치함
- `DONE`: spec 검증과 적대적 리뷰까지 완료함
- `DROPPED`: 근거를 기록하고 수행하지 않기로 결정함

## 작성 규칙

각 backlog 문서는 필요한 범위에서 다음을 포함한다.

1. 발견 출처와 기준 코드
2. 현재 코드·실측과 대조한 결과
3. `수용`, `부분 수용`, `보류`, `조사 필요`, `기각` 판정
4. 작업 항목 ID, 처리 시점, `Blocks`, 상태
5. 기존 개발 단계 사이의 삽입 지점
6. spec 승격 조건과 최소 완료 조건

상세 selector, 상태 전이 계약, 테스트 구현 순서와 코드 변경안은 작업 착수 후 spec에 작성한다. 같은 내용을 backlog와 spec에 중복해서 유지하지 않는다.
