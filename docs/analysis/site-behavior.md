## 1. 페이지와 예약 모달

- 매장 URL은 `https://app.catchtable.co.kr/ct/shop/<slug>` 형식이다. `[실측]`
- 예약하기를 누르면 SPA 안에서 달력 모달이 열리고 URL에 `date=YYMMDD`가 붙을 수 있다. `[실측]`
- 달력 모달 컨테이너에는 `role="dialog"`가 없다. `[실측]`
- 해시 형태의 CSS class는 빌드에 따라 바뀔 수 있으므로 선택자 근거로 사용하지 않는다.

### 1.1 예약창 진입 (2026-07-11 실측: 스시서정, 돗가비누각, 런던베이글뮤지엄 안국)

- 예약 진입 CTA는 매장 상세 하단 고정 dock `aside#dock` 내부의 `button`이며 텍스트가 `예약하기`다. `aria-label`은 없고 class는 해시이므로 `#dock` + 버튼 텍스트로 판별한다. `[실측: 스시서정, 돗가비누각]`
- CTA는 상세 하위 탭(예: `/ct/shop/<slug>/menuAllList`)으로 SPA 라우트가 바뀌어도 유지되며 동일하게 동작한다. `[실측: 스시서정]`
- CTA 클릭 시 풀 리로드가 일어나지 않는다(주입한 전역 계측 객체가 유지됨). `history.replaceState`로 현재 경로에 `date=YYMMDD` 쿼리만 붙고 같은 문서 안에서 달력 모달이 열린다. `[실측]`
- 클릭부터 달력 날짜 셀 렌더까지 약 287ms(스시서정)~350ms(돗가비누각). 시간 기준이 아니라 날짜 셀 관측 폴링으로 진입 성공을 판정해야 한다. `[실측]`
- 달력 월 머리글은 `YYYY년 M월` 텍스트의 button이며 이전·다음 월 button은 각각 `aria-label="Previous page"`, `aria-label="Next page"`다. 스시서정에서 2026년 7월 → 8월 → 7월 전환과 버튼 disabled 상태 변화를 확인했다. `[실측: 스시서정]`
- 모달 구성은 달력 + 인원 칩(기본 `2명` 선택) + 시간 슬롯 + `닫기` 버튼이 **한 모달**이다. 인원 선택은 달력에 선행하는 별도 단계가 아니다. `[실측]`
- 돗가비누각 모달 우상단에는 테이블 타입 필터 드롭다운(`전체`)이 있다. 가게별 변형이 존재한다. `[실측]`
- 선택 날짜가 매진이면 슬롯 대신 `빈자리 알림 신청` 버튼이 렌더된다. 이 버튼은 계정 알림을 등록하므로 자동화·실측 모두 클릭 금지다. `[실측: 돗가비누각]`
- 웨이팅 전용 매장은 dock에 `예약하기`가 없고 disabled 버튼 `현장 웨이팅만 가능`만 있다. 문서 전체에 `예약하기` 텍스트가 없었고 검색 진입 URL에 `type=WAITING`이 붙었다. 진입 단계는 이 상태를 예약 불가 매장으로 판별해 인계해야 한다. `[실측: 런던베이글뮤지엄 안국]`
- slug는 가독형(`sushi_sujung`)과 불투명 ID(`-dY58NRd-8bceTjORgjomw`) 두 형태가 존재한다. 검색 결과 화면은 `/ct/map/search-map` 경로다. `[실측]`
- 매장 페이지 본문에는 `예약 오픈 알림 받기` 버튼이 있을 수 있다. 계정 상태를 바꾸므로 클릭 금지다. 알림을 이미 등록한 매장에서는 `예약 오픈 알림 취소하기`로 바뀌며 마찬가지로 클릭 금지다. `[실측: 스시서정, 도량]`
- 예약+웨이팅 겸용 매장(도량)은 홈 탭 본문에 `예약`/`웨이팅` 세그먼트, `날짜 · 인원 · 시간` 드롭다운, 날짜 칩(`오늘 (토) 예약 가능`, `예약 마감`, `휴무`)이 있는 예약 위젯이 내장된다. 세그먼트는 `aria-hidden` span, 날짜 칩은 role·aria 없는 순수 `div`라 자동화 앵커로 쓸 수 없다. dock `예약하기`는 이 매장에서도 동일하게 달력 모달을 열므로(렌더 317ms) 진입 자동화는 dock CTA로 통일한다. `[실측: 도량]`
- 매진 알림 버튼의 변형: `저녁 시간대 빈자리 알림 신청`(돗가비누각), `저녁 시간대 빈자리 알림 신청 마감`(도량). `[실측]`

### 1.2 Mobiscroll 달력 변형 (2026-07-14 실측: 야키토리묵)

- 예약 모달이 열린 상태에서 기존 `div[role="button"][aria-label]` 날짜 셀은 0개였다. 날짜 셀에는 role, aria-label, data 날짜 속성이 없다. `[실측: 야키토리묵]`
- 달력에는 `.mbsc-calendar-table`이 3개 렌더되며 현재 월 하나만 `.mbsc-calendar-table-active`를 갖고 나머지는 `aria-hidden="true"`다. 단순한 geometry 가시성만으로는 비활성 테이블을 제외할 수 없다. `[실측: 야키토리묵]`
- 활성 테이블은 `.mbsc-calendar-row` 6개와 각 7개의 `.mbsc-calendar-cell.mbsc-calendar-day`로 구성된다. 표시 월 button은 `YYYY년 M월`, 월 이동 button은 기존과 같은 `Previous page`/`Next page` aria-label을 유지한다. `[실측: 야키토리묵]`
- 셀의 선두 숫자는 일자이며 현재 월 밖 셀에는 `.mbsc-calendar-day-outer`, 선택 셀에는 `.mbsc-selected`, 클릭 불가 셀에는 `.mbsc-disabled`가 붙는다. 셀에는 `오늘`, `마감`, `오픈 전` 같은 보조 문구가 추가될 수 있다. `[실측: 야키토리묵]`
- 활성 월, 6×7 셀 순서, 셀 선두 일자와 계산한 달력 날짜가 모두 일치할 때만 이 구조를 날짜 셀로 판독한다. Mobiscroll class 하나만으로 날짜를 추측하지 않는다. `[설계 근거가 된 실측]`

## 2. 슬롯 재조회

사이트는 다음 요청으로 슬롯을 조회하지만 요청 본문의 핵심 값은 암호화되어 있다.

```text
POST https://ct-api.catchtable.co.kr/api/reservation/v1/dining/time-slots
```

- 확장 프로그램은 이 API를 직접 호출하거나 암호화 요청을 재현하지 않는다.
- 다른 가용 날짜를 클릭하면 사이트가 슬롯을 다시 조회한다. `[실측]`
- 이미 선택된 날짜를 다시 클릭하면 슬롯을 다시 조회하지 않는다. `[실측]`
- 따라서 리페치 프리미티브는 `인접 가용 날짜 -> 목표 날짜` UI 토글이다.
- 인원 칩 토글이 재조회 트리거인지 여부는 미실측이다.

## 3. 날짜 셀

실측된 날짜 셀의 안정 속성:

```html
<div
  role="button"
  aria-label="화요일, 7월 28, 2026"
  aria-pressed="true"
  aria-disabled="true"
></div>
```

- 기본 선택자: `div[role="button"][aria-label]`
- `aria-label`은 `요일, M월 D, YYYY` 형식이며 연·월·일을 모두 비교한다.
- 오늘 날짜 셀은 `오늘, 일요일, 7월 12, 2026`처럼 `오늘,` 접두가 붙는 변형이 존재한다. 셀렉터 `div[role="button"][aria-label]`로는 잡히지만 `^요일,`로 엄격 파싱하면 오늘 셀을 놓친다. 연·월·일 숫자 비교로 판정해야 안전하다. `[실측: 이시즈에 2026-07-12]`
- 현재 선택 날짜는 `aria-pressed="true"`다.
- 선택 불가 날짜는 `aria-disabled="true"`다. 선택 가능한 셀에는 이 속성이 없을 수 있다.
- 이전·다음 달 셀도 함께 렌더링되므로 날짜 숫자만 비교하면 안 된다.

## 4. 시간 슬롯

실측된 슬롯 칩:

```html
<button data-busy="false" data-duplicate-index="3" aria-hidden="true">
  <span>오후 3:00</span>
</button>
```

- 기본 선택자: `main button[data-busy]`
- 캐러셀 복제 노드가 다수 존재하며 `aria-hidden="true"`는 제외한다.
- 시간 슬롯에는 `aria-disabled`가 존재하지 않았다. 과거 `main button[aria-disabled]`는 0개를 반환한 잘못된 선택자다.
- 시간 표기는 `오전|오후 H:MM` 형식이다.
- `data-busy="false"`인 표시 슬롯만 후보로 취급한다.
- 같은 시각의 복제 노드는 시간 문자열로 중복 제거한다.
- 매진 시간이 비활성 칩으로 남는지, DOM에서 제거되는지는 미실측이다.

## 5. 인원

### 5.1 인원 칩 안정 앵커 (2026-07-11 실측: 도량, 스시서정)

기존 "안정 속성 없음" 판단은 leaf span/`div[role=button]`만 봐서 나온 오판이었다. 칩은 네이티브 라디오를 감싼 `label`이다.

- 선택자: `input[type="radio"][name="personCount"][value="<N>"]`, `label`로 래핑됨. `[실측: 도량, 스시서정]`
- 선택 상태: 네이티브 `input.checked`. 현재 선택은 `input[name="personCount"]:checked`. `[실측]`
- 모달은 기본 `2명`(`value="2"` checked)으로 열린다. 따라서 `personCount=2`는 무동작으로 충족된다. `[실측]`
- 선택 동작: `label`(또는 input) 클릭 → `checked` 전환 + URL에 `personCount=<N>` 부착. 도량에서 3명 선택 후 2명 복원까지 실측했다. `[실측]`
- 라디오는 가로 목록에 다수 렌더된다. 스시서정은 `value=1..80`인 80개가 모두 유일했고, 화면 밖 항목도 같은 목록 안의 유효 옵션이었다. hidden/`aria-hidden` 노드는 제외하되 단순히 viewport 밖이라는 이유로 제외하면 안 된다. 방어적으로 `value` 중복은 제거한다. `[실측: 스시서정]`
- 값 범위는 표시된 "최대 N명"보다 큰 라디오까지 존재했다(도량 표시 12명, 라디오는 21+). 실제 선택 가능 상한은 미확정이므로 자동 설정은 대상 매장에서 확인 후 진행한다.
- 인원 변경이 슬롯 재조회를 트리거하는지는 여전히 미실측이다.

## 7. 슬롯 클릭 이후

태오 광안리에서 슬롯 클릭 뒤 다음 구조를 실측했다.

- `div[role="dialog"][aria-label="테이블 타입 선택"]`
- 옵션: `label[role="radio"][aria-label]`
- 상태: `aria-checked`, `aria-disabled`
- 진행: dialog 내부 `다음` 버튼

스시서정에서는 테이블 화면 없이 다음 선택적 단계가 이어졌다.

- 메뉴: `div[role="dialog"][aria-label="메뉴 선택"]`
- 메뉴 옵션: `button[role="checkbox"][aria-label]`, 상태 `aria-checked`
- 예약금 방법: `div[role="dialog"][aria-label="예약금 결제 방법 선택"]`
- 예약금 0원: `input[type="radio"][aria-label="예약금 0원 결제"]`
- 진행 후 URL: `/ct/reservation/form?isDepositFree=1&openRegisterCard=0`

하오카오스탠에서 다음 추가 상품 구조를 실측했다.

- `div[role="dialog"][aria-label="추가 상품"]`
- 상품별 감소·증가 버튼과 수량 `0`
- dialog 하단 `이전`, `다음` 버튼
- 상품을 선택하지 않은 초기 상태에서도 `다음` 버튼 활성

중간 단계는 식당마다 없거나 조합이 다를 수 있으므로 고정 순서를 가정하지 않는다. 예약 폼의 방문 목적, 약관, 결제, 최종 `예약하기`는 자동화하지 않는다.

돗가비누각에서 2026-07-11에 수량형 메뉴 선택 dialog를 실측했다. 같은 `aria-label="메뉴 선택"`이지만 checkbox가 없고 메뉴별 수량으로 필수 메인 메뉴를 선택한다.

- 수량 표시: `input[type="number"][aria-label="<메뉴명> 수량"]`
- 수량 조절: `button[aria-label="<메뉴명> 수량 추가"]`, `button[aria-label="<메뉴명> 수량 감소"]` (수량 0이면 감소 버튼 disabled)
- 진행 버튼(`다음` 또는 `확인`)은 수량 미달이어도 DOM에서 항상 활성이며, 클릭해도 화면이 전환되지 않고 `메인 메뉴를 선택해주세요` 안내만 남는다. `[실측]`
- 필수 총수량은 예약 인원수와 같다. 인원 2명에서 수량 1은 진행 클릭이 무시됐고 수량 2는 다음 화면으로 전환됐다. `[실측]`
- 인원수 초과로 추가를 누르면 `예약 인원(N명) 보다 많이 선택할 수 없는 메뉴입니다` 안내가 표시된다. `[화면 증거]`
- 메뉴 단가는 예약금으로 표시되므로(`위 금액은 예약금입니다`) 수량만큼 보증금이 커진다.

하오카오스탠에서 2026-07-11에 유료 예약금 안내 dialog를 실측했다.

- `div[role="dialog"][aria-modal="true"][aria-label="예약금 안내"]`
- 내용: 1인당 예약금, 총 인원, 합계, 환불정책 안내 텍스트
- 진행: dialog 하단 `이전`, `확인` 버튼 (aria 속성 없는 일반 button, 표시 시점부터 활성)
- `확인` 클릭은 안내 확인일 뿐 결제 실행이 아니다. 결제와 최종 확정은 예약 폼 이후 단계다.

같은 날 당일 예약 흐름에서 `div[role="dialog"][aria-label="오늘 방문이 맞으신가요?"]`(버튼 `취소`/`확인`)도 실측했다. 오픈런 대상은 미래 날짜이므로 MVP는 이 dialog를 자동 진행하지 않는다.

사용자 제공 화면에서 다음 변형도 확인됐다. 아직 DOM 역할과 속성은 실측하지 않았다.

- `예약금 0원 결제란?` 안내와 `0원 결제로 예약` 버튼 `[화면 증거]`
- 예약 폼 도착 뒤 덮는 홍보 안내 창과 단일 `확인했어요` 버튼. 등장 여부와 렌더 시점이 비결정적이며 폼 도착보다 늦게 나타날 수 있다. 버튼 클릭으로 닫히는 것은 실측했다. `[화면 증거+실측]`

추가 상품은 수량 버튼을 누르지 않고 활성화된 `다음`만 클릭한다. `다음` 또는 메뉴의 `확인`이 일시적으로 비활성 상태면 실패로 판정하지 않고 후속 단계 제한 시간 안에서 활성화를 기다린다. 화면 전환 중 이전 dialog와 새 dialog가 함께 남으면 렌더된 dialog 중 DOM 순서상 마지막 화면을 현재 단계로 판정한다.

### 7.1 dialog 전환 중 일괄 비활성 (2026-07-11 실측)

하오카오스탠 테이블 타입 dialog에서 `다음` 클릭 직후 전환 타임라인을 실측했다.

## 8. 서버 시계

- 같은 오리진 매장 URL에 `HEAD` 요청을 보내면 신선한 `Date` 헤더를 읽을 수 있었다. `[실측]`
- `robots.txt`는 CDN 캐시된 응답을 반환해 시계 기준으로 사용할 수 없다. `[실측]`
- HTTP Date는 1초 해상도이므로 여러 표본에서 초 값이 바뀌는 경계와 RTT를 함께 측정해야 한다.
- **표본 5개(성긴 간격)에서는 오프셋이 여러 군으로 갈라지는 것처럼 보였으나, 표본 9개(기본값)로는 단일 시계의 정상 톱니파로 수렴한다.** 2026-07-12 5샘플 실런들에서는 연속 샘플의 로컬 경과 ~200ms 동안 Date 헤더가 2초 점프하는 것처럼 보여 "서버 풀 간 시계 편차"로 해석했다(worklog 08). 그러나 같은 날 9샘플 실런(worklog 11)에서는 오프셋이 각 Date 초 구간 내에서 샘플 간격(~125~150ms)마다 일관되게 ~200~240ms씩 선형 감소하는 정상 톱니파를 보였고, 초기·최종 보정이 78ms 차이로 수렴했다(−38ms vs +40ms). 즉 5샘플 관측은 성긴 표본·지연 변동에 의한 앨리어싱(착시)이었을 가능성이 높다 — 풀 편차 자체를 완전히 배제할 순 없으나, **표본 9개(기본값)를 쓰면 실용적으로 문제가 재현되지 않는다.** `[실측: 이시즈에, worklog 08/11]`

### 8.1 슬롯 XHR (2026-07-12~13 실측: 이시즈에·누와·야키토리묵)

**엔드포인트 (R1).** 슬롯 목록은 `POST https://ct-api.catchtable.co.kr/api/reservation/v1/dining/time-slots?shopRef=<ref>` — **app 오리진이 아니라 별도 API 호스트(Cloudflare 경유)**다. 본문은 `encryptedParamString`(재현 불가 — 직접 호출 금지 유지), 단 요청 헤더에 `yymmdd`(날짜)·`personcount`가 평문으로 실린다. **URL에는 날짜가 없다** → 리소스 타이밍 항목만으로는 어느 날짜의 응답인지 구분 불가(도착 신호는 날짜 불문). 레이트리밋 헤더 `x-ratelimit-*` burst 1200 — 우리 클릭 빈도에서 무해. `[실측]`

**발사 조건 (R2).** 달력 날짜 셀 클릭마다 `time-slots`가 1회 발사된다(인접→목표 각각). **같은 날짜(aria-pressed=true) 재클릭은 재발사 없음, DOM 변화도 없음** → 갱신 강제에는 인접 토글이 필수(현행 전략 검증됨). `[실측]`

**파이프라인 지연 (R3).** 클릭 → XHR 발사 **217~379ms**(SPA 내부 지연, n=5), XHR 왕복 52~63ms, responseEnd → 슬롯 DOM 렌더 **56~182ms**. 클릭→렌더 합계 ≈ **330~560ms**. 날짜 클릭 시 기존 슬롯 DOM은 발사 시점(클릭+~280ms)에 비워진다 — 그 전까지 이전 날짜의 슬롯이 잔존 표시된다. `[실측]`

**응답 형태 (R5).** 가용 여부와 무관하게 항상 200 + `data.timeSlotMap`(시각→`{availableYn, date, time, ...}`) 구조. 도착 신호는 항상 발생하므로 가용 판정은 DOM(또는 바디) 스캔이 담당해야 한다. payload에 ms 서버시각 필드 없음(`resp2`는 ID). `[실측]`

**푸시 채널 없음 (R6, 2026-07-13 실측).** WebSocket/EventSource 생성자를 페이지 로드 전부터 후킹하고 새로고침→예약하기→날짜 토글 전 과정을 돌린 결과 **생성 0건**. 전체 네트워크 538건에도 websocket/eventsource 타입 부재. 스택은 tanstack-query 기반 REST 폴링. 추가로 엄밀 확인(같은 실측 세션): `text/event-stream` content-type 응답 0건, 3초 이상 유지되는 fetch 0건(사용자 기준 "수십 초"보다 엄격한 임계), Worker/SharedWorker 생성 자체 0건(내부 WebSocket 가능성도 배제). **서버 푸시(SSE/WS)가 없으므로 슬롯 오픈은 클라이언트가 요청해야만 알 수 있다 — 관찰할 푸시 이벤트 자체가 존재하지 않는다. REST 요청-응답형으로 확정.** 따라서 감지는 UI 토글로 사이트 XHR을 유발하고 그 응답 전이를 트리거로 삼는 구조가 유일하다(availability 요청 본문 `encryptedParamString` 암호화로 직접 호출도 불가). `[실측: 이시즈에]`

**격리 월드 가시성 (R4).** content script(격리 월드)의 PerformanceObserver가 `time-slots` 리소스 항목을 정상 관측한다 — 2026-07-12 23:05 안전 점검 실런에서 `watch:"live"`·`xhrArrivalServerAtMs` 기록 확인(worklog 13). `[실측]`

**transport·상관관계 재확인 (2026-07-13).** 누와·이시즈에·야키토리묵에서 `PerformanceResourceTiming.initiatorType`과 임시 XHR hook을 교차 확인한 결과 실제 transport는 `XMLHttpRequest`였다. 요청에는 `x-requested-with: XMLHttpRequest`가 있고, `setRequestHeader`에서 `yymmdd`·`personcount`를 읽을 수 있다. URL에는 날짜가 없고 암호화된 요청 body는 저장·복제하지 않는다. `[실측]`

**응답 판독 (2026-07-13).** XHR `responseType`은 기본 text이고 `responseText`를 `JSON.parse`할 수 있었다. 응답의 `data.inputDate`, `data.personCount`, `data.timeSlotMap`으로 요청과 결과를 교차 검증할 수 있다. 누와의 빈 응답은 `timeSlotMap: {}`였고, 이시즈에의 가용 응답은 `"1830"`, `"1900"` 같은 HHmm key와 boolean `availableYn: true`를 사용했다. `tableType`은 문자열이지만 가용 판정 외 정책 근거로 쓰지 않는다. `[실측]`

**body→DOM 선행 시간 (2026-07-13).** 이시즈에의 warm 날짜 토글 3회에서 XHR `loadend`에서 body를 분류한 뒤 표시 가능한 `button[data-busy="false"]`가 처음 관측될 때까지 각각 **24.3ms, 30.0ms, 19.1ms**였다. send/loadend 시점에는 슬롯 DOM이 비어 있었고 이후 버튼이 렌더됐다. 이전 56~182ms 측정과 환경·관측 지점이 다르며 실제 오픈 순간 측정도 아니므로, 현재 결론은 "최대 25ms DOM 폴링 일부를 줄일 가능성"이지 클릭 경로 전환 근거가 아니다. `[실측: 이시즈에, warm toggle]`

**실제 오픈 empty→populated (2026-07-14, 조광201).** 00:00 오픈 잡에서 목표 날짜 body가 오픈 전 약 -553ms에 `EMPTY`, 오픈 후 약 +956ms에 `POPULATED`로 전환됐다. 성공 XHR은 target 날짜 클릭 +854ms, XHR 발사 약 +906ms, body 분류 약 +956ms, 표시 DOM 후보 관측 +1004ms, 20:00 슬롯 클릭 +1011ms 순서였다. body/DOM 후보는 일치했고 body가 DOM보다 **47.7ms** 선행했다. 시각은 app 호스트 HEAD ReferenceClock 기준이며 감지 시점 uncertainty는 125ms다. 34/34 events, dropped 0, 최종 `HANDED_OFF`를 확인했고 화면 녹화로 슬롯 클릭과 예약 폼 인계를 교차 확인했다. `[실측: 조광201, run-c5463a0b-ffe0-447b-a619-f9c545181ac0]`

**실제 오픈 조건 불일치 음성 표본 (2026-07-14, 양주르).** 목표 날짜 `2026-09-05`, 2명 조건에서 target body가 `EMPTY -> POPULATED`로 전환되고 cycle 6, requestSequence 12, `EXACT`로 상관됐다. 화면에 열린 슬롯은 11:00·15:00·15:30·17:30이었고 실행 설정 범위는 18:30-21:00이어서 선택 가능한 후보가 없었다. 따라서 슬롯을 클릭하지 않고 탐색을 계속한 것은 정상이다. 같은 구간의 cycle 없는 `NONE/IRRELEVANT` shadow는 target wake 증거가 아니며 제어에 사용되지 않았다. 마지막 달력 상태 변경 종료는 측정 중 사용자 클릭으로 발생해 자동화 결과에서 제외한다. 이 실행은 분류와 미클릭 안전성의 음성 표본이며, 일치 슬롯의 body wake 성능 표본은 아니다. `[실측: 양주르, run-866b9478-ff60-4429-977b-0ea012eefdaa]`

**실제 오픈 일치 슬롯과 화면 상태 차이 (2026-07-15, 누와).** 정상 크기로 전면에 둔 실행에서 target 날짜 클릭 +690ms, 슬롯 XHR resource arrival +814ms, 18:00 DOM 후보 감지 +884ms, 클릭 +893ms, 예약금 안내 확인 +1560ms, 예약 폼 최초 관측 +1857ms, 인계 이벤트 +2253ms를 기록했다. 폼 관측 뒤 안내 처리 유예 때문에 인계 이벤트가 약 396ms 늦게 기록됐다. 시각은 최종 ReferenceClock 기준이고 감지 시 uncertainty는 29ms다. `EXACT POPULATED` body response는 DOM보다 약 74ms 빨랐지만 bridge 전달에 약 57ms가 걸려 bridge 이후 DOM 선행 여유는 약 16ms였다. body는 이전 cycle로 도착해 `inactive_cycle`로 거절됐고 다음 cycle의 기존 DOM 경로가 슬롯을 찾았다. 36/36 events, dropped 0이며 최종 예약 완료는 폼 인계 뒤 사용자가 확인했다. [실측: 누와, run-ec3acf59](../evidence/live-runs/2026-07-14/nuwa-run-ec3acf59-2e31-48c5-a558-b7dd184d7a01/run.csv)

같은 PC의 최소화 실행에서는 cycle 1 `EXACT POPULATED` body wake를 수용했지만 response-to-DOM 약 606ms, wake-to-DOM 약 482ms로 250ms body window를 넘겨 fallback했다. 슬롯 클릭은 서버 기준 약 +1297ms에 전달됐으나 5초 안에 후속 화면을 확인하지 못했고 종료 스냅샷에는 슬롯 모달이 남았다. 다른 최소화 실행에는 약 2초 이상의 cycle과 20~37초 공백이 나타났다. 화면 상태와 지연의 연관성은 강하지만 현재 trace에는 visibility·focus·viewport가 없어 인과관계로 확정하지 않는다. [실측: 누와, run-5881d898](../evidence/live-runs/2026-07-14/nuwa-run-5881d898-a394-4244-a694-07e2d5ea0205/run.csv), [run-8984299b](../evidence/live-runs/2026-07-14/nuwa-run-8984299b-a323-4278-a799-4da514d9c20a/run.csv)

**resource arrival 상관관계 제한 (2026-07-14).** 위 실런의 cycle 2·3에는 날짜 불문 `PerformanceResourceTiming` arrival과 DOM `NO_SLOT`은 남았지만, 동일 목표 날짜·인원으로 검증된 body 이벤트가 없다. URL에 날짜가 없으므로 canceled 인접 요청의 resource 종료도 `lastArrivalAt`을 갱신할 수 있다. 따라서 resource arrival 단독 값은 target body 응답 증거가 아니며, 제어 경로에 사용할 때는 `yymmdd`·`personcount`가 검증된 body 이벤트와 구분해야 한다. `[실측: 조광201]`

**같은 문서의 시간축 (2026-07-13).** `chrome.scripting.executeScript`로 같은 탭의 MAIN/ISOLATED world를 연속 측정한 결과 `performance.timeOrigin`이 정확히 같았다. `performance.now()` 절대값은 같은 document 안에서 직접 비교할 수 있으며, 연속 실행으로 생긴 epoch-now 차이는 2.4ms였다. 문서가 교체되면 time origin도 바뀌므로 probe channel은 런·document 수명에 묶어야 한다. `[실측: 이시즈에]`

**테이블 타입 변형 (2026-07-13).** 야키토리묵 응답에서 `onlineTableTypeUseYn: true`, `onlineTableTypeList: ["H", "B"]`를 확인했다. 슬롯의 `tableType`은 요청 조건에 따라 `""` 또는 `"H"`였다. 이 코드는 진단용으로만 보관하며 홀/바 자동 선택 정책이나 클릭 근거로 해석하지 않는다. `[실측]`

**미확정.** 실제 오픈 empty→populated는 일치 슬롯 3개 실행과 조건 불일치 음성 표본을 확인했지만, body wake가 fallback보다 빠르게 후보를 찾은 실제 오픈 표본은 아직 없다. 반복 실행의 응답 역전 빈도, 매장별 공개 지연 분포, ct-api 호스트와 app 호스트의 절대 시계 편차, visibility·viewport 영향은 아직 미확정이다. 한 표본의 공개 지연을 매장 또는 서버의 일반 특성으로 단정하지 않는다.

### 8.2 장거리 월 이동과 클릭 유실 (2026-07-15 실측: 뽈뽀)

뽈뽀의 예약 달력은 Mobiscroll 단일 달력이다. 기본 진입 시 2026년 7월을 표시했고, 보이는 월 제목 버튼과 `Previous page`/`Next page` 버튼은 각각 하나였다. `Next page` 정상 클릭 후 월 제목 DOM은 7월 -> 8월 약 24ms, 8월 -> 9월 약 44ms에 변경됐다. `[실측: 뽈뽀]`

같은 매장의 목표 날짜 `2026-09-06` 실행 로그에서는 7월 화면에서 첫 `Next page` action 뒤 표시 월이 바뀌지 않았고, 추가 클릭 없이 10초 뒤 종료됐다. 따라서 장거리 이동 자체의 정상 지연이 아니라 클릭 한 번이 유실될 수 있는 실행 환경과 기존 무한 pending의 결합으로 분류한다. 월 전환은 표시 월 재확인을 기준으로 bounded retry해야 하며, 단순히 여러 번 연속 클릭해서는 안 된다. [실측: run-188c11c0](../evidence/live-runs/2026-07-15/bistropolpo-run-188c11c0-5cb0-45ca-8fdf-1719782126ab/run.csv)

## 10. Fixture 출처 규칙

테스트 fixture에는 이 문서의 실측 구조만 포함하며, 파일 상단에 실측일·화면·출처를 기록한다. 테스트 편의를 위해 실제로 없던 속성을 추가하지 않는다.
