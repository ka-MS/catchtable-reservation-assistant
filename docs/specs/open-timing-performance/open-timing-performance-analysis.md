# 오픈 타이밍 성능 패키지 — 공통 분석

**기준일:** 2026-07-13
**대상:** 예약 오픈 순간의 슬롯 확보(감지→클릭→진입) 속도·정확·견고성
**성격:** 우산(umbrella) 패키지. 세 하위 티어(01/02/03)를 관통하는 진단과 근거를 여기 한곳에 모은다. 다른 세션·AI는 각 티어 폴더를 읽기 전에 이 문서를 먼저 읽는다.

## 0. 한 줄 요약

> 서버 기준시계는 오픈 구간에 **늦지 않게 진입**하기 위한 보조값으로만 쓰고, 실제 예약 진입은 예약 API의 **슬롯 응답(빈→채워짐 전이)**이 트리거한다. 시계가 ±1초 틀려도 슬롯 응답 전엔 클릭하지 않고, 응답이 오면 시계와 무관하게 즉시 클릭한다.

## 1. 사고 전말 (2026-07-13 에스콘디도 실오픈)

실제 오픈(에스콘디도, 9:00:00)에서 슬롯 클릭이 **우리 프레임 +1369ms**에 일어났다. 처음엔 "에스콘디도 서버가 슬롯을 1.3초 늦게 열었다"고 해석했으나, 오판이었다.

| 사이클 | 인접 클릭 | 목표 클릭 | XHR 도착 | 결과 |
|---|---|---|---|---|
| 1 | −123ms | −19ms | +88 | NO_SLOT |
| 2 | +371 | +446 | +502 | NO_SLOT |
| 3 | +775 | +846 | +903 | NO_SLOT |
| 4 | +1178 | +1246 | **+1320** | **SLOT_FOUND** |

- 감지 +1359ms(도착 39ms 뒤), 클릭 +1369ms. watch=live 전 사이클(격리 월드 감시 정상).
- 시계 보정: 초기 boundary +997(±202), 최종 median +1009(±530). **둘 다 오프셋 ~+1000ms로 일치.**

### 1.2 독립 검증 — 진짜 오프셋은 ~0ms (시계가 틀렸다)

같은 세션에서 3중으로 교차검증했다.

1. **네이비즘(독립 기준) = 로컬 PC 시계.** 네이비즘 서버시각 `09:31:10`일 때 로컬 `09:31:10.391` — 같은 초. 오프셋이 +1000이면 네이비즘이 1초 앞서야 하는데 아니다.
2. **HEAD 요청 24개 중 17개가 오프셋 ~0, 7개만 +1초.** 원자료에서 로컬 초와 서버 Date 초가 대부분 일치하고, 일부만 +1초 앞섰다.
3. **즉석 boundary 측정이 +28 / +1039 / +1056 / +1118로 갈렸다.** 어느 서버 쌍이 걸리느냐에 따라 값이 ~1000ms 튄다.

**결론: `app.catchtable.co.kr` 뒤에 시계가 ~1초 어긋난 서버 풀이 섞여 있고(다수 ~0, 소수 +1초), 우리 clock-sync가 소수 스큐 풀에 락됐다.** 진짜 오프셋은 ~0이다.

### 1.3 재해석 — 서버는 정상, 시계만 틀렸다

우리가 오프셋을 +1000으로 잘못 추정 → serverClock = 로컬 + 1000 → "지금 9:00:00"이라 판단한 순간의 진짜 서버시각은 8:59:59 → **~1초 일찍 토글 시작**(사용자가 눈으로 본 "오픈 전 토글"의 정체). 로그의 "+1320ms 도착"을 진짜 프레임으로 환산하면 **+320ms** — 에스콘디도는 정시에 열었고 슬롯은 ~320ms 뒤에 떴다. 클릭도 진짜로는 **~+370ms**.

**핵심 교훈:** 감지·클릭 기계는 진짜 프레임 기준 잘 작동했다(도착 39ms 뒤 감지, 49ms 뒤 클릭). 이번 사고의 유일한 원인은 **기준시계 추정 오차 ~1초**다. 그리고 단일 프레임(우리 시계) 로깅이 오판을 유발했다.

## 2. 실측 제약 (설계를 강하게 구속한다)

xhr-slot-watch 정찰(worklog 12, site-behavior §8.1)과 이번 시계 검증에서 확정한 제약:

- **P1. 슬롯 API 직접 호출 불가.** `POST ct-api.catchtable.co.kr/.../time-slots`의 본문은 `encryptedParamString`으로 암호화(재현 불가). 리페치는 **UI 토글(인접→목표 날짜 클릭)로 사이트가 스스로 요청을 쏘게 하는 방식**이 유일하다. 동시 다중 직접요청·stagger는 불가.
- **P2. 슬롯 응답은 시계 표본이 못 된다.** ct-api는 별도 호스트(CORS)이고 `Date` 헤더를 노출하지 않으며(`access-control-expose-headers`에 없음) payload에 ms 서버시각 필드도 없다. 따라서 **시계 표본은 same-origin `app` HEAD 요청**에서, **슬롯 감지는 availability 응답/DOM**에서 — 두 스트림으로 분리된다.
- **P3. `app` HEAD의 `Date`는 예약 서버 시계가 아닐 수 있다.** CDN/프록시/게이트웨이 시계일 수 있어, 오픈을 판정하는 ct-api 애플리케이션 서버 시계와 같다는 보장이 없다. 그래서 이 시계는 **`ReferenceClock`**(오픈 구간 접근용 관측 기준값)이지 절대 진실이 아니다.
- **P4. 클릭 트리거는 이미 응답 주도(부분).** 현재 감지는 "네트워크 도착 신호로 가속된 DOM 기반 감지"다(worklog 13). 보장 불변식은 "슬롯 DOM이 뜨기 전엔 클릭 안 함". 응답 body의 빈→채워짐을 직접 보는 구조는 아직 아니다.

## 3. 근본 원칙: 응답 주도, 시계는 보조

정확한 외부 표준시계조차 최종 트리거로 믿으면 안 된다. 가장 강한 진실은 **예약 API가 슬롯을 반환한 순간**이다. 따라서:

```
ReferenceClock  = 늦지 않게 고빈도 감시를 시작하기 위한 보조값 (±오차 허용)
Availability 응답/DOM = 실제 오픈의 ground truth (클릭 트리거)
```

불변식(모든 티어가 지켜야 함):
- 시계가 ±1초 틀려도 **슬롯 응답 전에는 예약 진입하지 않는다.**
- 슬롯 응답이 오면 **시계가 틀려도 즉시 진입한다.**

## 4. 왜 세 티어로 쪼갰나

세 가지 모두 "오픈 순간 성능 강화"라는 한 목표를 향하지만, 관심사·검증 방법·위험이 달라 별도 스펙으로 끊는다. 섞으면 실오픈 검증 결과의 인과가 흐려진다.

### Tier 1 — `01-reference-clock-reliability` (이번 사고 직결, 최우선)

기준시계가 스큐 풀에 락돼 ~1초 틀린 것이 사고의 유일한 원인. 오픈 진입 시점을 정확·정직하게 만든다.

- 오픈 직전 5~9개 **버스트 → 대기 시간 내내 시간 분산 rolling 샘플링**
- `Date`를 점이 아니라 **구간 `[D−t1, D+1000−t0]`**으로 보고, 1차원 **최대 피복(max-coverage)** 지점으로 오프셋 추정
- 경쟁 클러스터(스큐)면 **확신하지 않음** — LOW confidence + 넓은 uncertainty 출력
- 오케스트레이터는 offset이 아니라 **uncertainty를 보고 armLead(감시 조기 시작)** 결정. 클릭은 여전히 응답 주도
- **3-프레임 텔레메트리**(monotonic / reference-clock / availability)로 다시는 프레임 혼동 없게

**성공 기준:** 시계 오차 0이 아니라 — "모호하면 낮은 confidence·넓은 uncertainty로 정직하게 내리고, 그만큼 일찍 관측을 시작해 실제 슬롯 응답을 놓치지 않는다."

### Tier 2 — `02-availability-hot-path` (지연 최적화)

클릭 경로를 응답 body 직접 감지로 승격. 기존 `xhr-slot-watch` 패키지(도착 신호+DOM 스캔)의 연장선.

- **MAIN-world fetch/XHR 후킹**으로 응답 body의 빈→채워짐 전이를 직접 판정 → DOM 렌더 지연(실측 56~182ms) 건너뜀
- 기존 PerformanceObserver 도착 감지·DOM 스캔은 폴백으로 유지
- 다중 감지기가 생기므로 **원자적 claim guard**(런당 OBSERVING→CLAIMING 1회) 필수 — 이 티어에서 도입
- 응답 순서 역전·중복 populated 처리

착수 전 **Tier 1 실오픈 검증 후** 세부 핫패스 계측(body 완료→파싱→전이 판정→클릭)으로 필요성 확정.

### Tier 3 — `03-runtime-resilience` (견고성)

- 오픈 직전 탭 활성화·창 포커스(배경 탭 타이머 스로틀 회피)
- Service Worker 재시작 시 런 상태 reconcile, 페이지 새로고침 재주입
- 실패 주입 테스트(스큐 60%, 50:50 클러스터, RTT 급증, 응답 역전, 탭 hidden, SW 종료 등)

## 5. 티어 경계 요약

```
Tier 1  ReferenceClock 신뢰성   — 진입 시점 정확·정직 (클릭 경로 변경 금지)
Tier 2  Availability 핫패스     — 응답→클릭 지연 최소화 + claim guard
Tier 3  런타임 견고성           — 탭·SW·실패 복원력
```

## 6. 진단 재현 레시피 (콜드 세션용)

이 문서의 주장(풀 스큐·시계 오차)은 재측정으로 검증 가능하다. `use-chrome-devtools` + `catchtable-recon` 스킬로 로그인된 캐치테이블 탭에서:

1. **HEAD 오프셋 클러스터 측정.** same-origin 매장 URL에 `fetch(..., {method:"HEAD", cache:"no-store"})`를 ~70ms 간격 24회. 각 응답의 `Date`(초)와 로컬 `Date.now()` 초를 비교. 다수가 일치(오프셋~0)하고 일부가 +1초면 풀 스큐다. `serverDateMs`가 로컬 경과보다 크게 앞서 점프하는 표본이 스큐 풀.
2. **boundary 반복 측정.** 같은 측정을 여러 번 하면 boundary 오프셋이 ~0과 ~+1000으로 갈린다 → 스큐 확정. 한 번의 boundary만 믿으면 안 되는 이유.
3. **네이비즘 교차검증.** `time.navyism.com/?host=app.catchtable.co.kr` 탭의 표시 서버시각을 로컬 `Date.now()`와 같은 순간 읽어 비교. 같은 초면 진짜 오프셋 ~0.
4. **텔레메트리 재해석.** IndexedDB `catchtable-reserve-telemetry`의 실오픈 run에서 CLOCK_SYNCED `clockOffsetMs`가 ~+1000인데 위 재측정이 ~0이면, 그 run은 스큐에 락된 것. openDelta에 그 오차를 빼서 진짜 프레임으로 환산.

## 7. 거부한 대안과 이유 (재발 방지 — YAGNI)

외부 피드백에서 제안됐으나 우리 실측 제약상 채택 안 함. 다시 제안하기 전에 이 근거를 반박해야 한다.

| 제안 | 거부 이유 |
|---|---|
| availability API 직접 호출(DIRECT_PROBE) | 본문 `encryptedParamString` 암호화·재현 불가(P1). UI 토글만 가능. |
| 동시 다중 요청·stagger 폴링 | 요청이 UI 토글 유발이라 다중 토글은 DOM 충돌. 적용 불가. |
| availability 응답을 시계 표본으로 재사용("한 요청 두 역할") | ct-api는 CORS로 `Date` 미노출·payload에 ms 시각 없음(P2). 시계는 app HEAD로 분리. |
| 128표본 NTP급 통계 필터 | 시간 분산 rolling + 구간 최대피복으로 충분. 링버퍼 64로 시작, 과설계 회피. |
| 클러스터 단순 최다지지 확정 | 오염 클러스터가 과반이면 틀린 값 확정. "모호하면 LOW confidence"가 올바른 요구. |

## 8. 잔여 미지수 (과신 금지)

- **어느 풀이 오픈을 판정하나?** 우리는 다수 풀(~0)이 진짜라고 결론했으나, 예약을 실제로 여는 ct-api 애플리케이션 서버가 스큐 풀(+1초) 시계로 도는 가능성을 완전히 배제하진 못했다. 그래서 시계를 절대 트리거로 쓰지 않고(응답 주도), armLead를 넉넉히 잡아 어느 쪽이든 놓치지 않게 한다. 이 미지수가 응답주도 설계의 존재 이유다.
- **스큐 폭·빈도의 변동.** 스큐가 항상 ~+1초인지, 매장·시간대별로 다른지 미실측. Tier 1 rolling 로그로 계속 관측.
- **매장 교차 확인.** 시계 스큐는 호스트 단위라 매장 무관할 것으로 보이나, 슬롯 등장 지연은 매장별로 다를 수 있음(에스콘디도 ~320ms). 다른 매장 실오픈으로 확인 필요.

## 9. 용어 계약 (전 티어 공통)

- **ReferenceClock**: app HEAD `Date`로 추정한 기준시각. 오픈 구간 접근용 관측값이지 예약 서버의 절대 진실이 아니다. 코드·필드는 `ReferenceClock*`/`reference*`로 명명. `ServerClock` 금지(거짓 권위 함의).
- **armLead**: 감시(토글) 단계로 조기 진입하는 리드타임. uncertainty 상한 기반. 클릭을 앞당기는 값이 아니다.
- **populated 전이**: availability 응답/DOM이 빈 슬롯→채워진 슬롯으로 바뀌는 순간. 유일한 클릭 트리거.
- **3-프레임**: monotonic(런 경과) / reference(기준시각 오픈 대비) / availability(empty·populated·DOM·클릭 시점). 로그는 셋을 함께 싣는다.
