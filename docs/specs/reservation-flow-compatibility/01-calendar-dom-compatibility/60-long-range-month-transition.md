# 장거리 예약 날짜 월 전환 보강

## 관찰

2026-07-15 `bistropolpo`, 목표 날짜 `2026-09-06` 실행에서 첫 `Next page` 클릭 뒤 표시 월이 계속 `2026년 7월`로 남았다. 실행 로그에는 월 이동 action 1건만 남았고, 10초 뒤 다음 오류로 종료됐다.

```text
목표 월 또는 날짜 선택 상태를 제한 시간 안에 확인할 수 없습니다.
```

종료 스냅샷도 `오늘 | 2026년7월 | 닫기`였으므로, 첫 클릭 무효화 뒤 재시도가 없었던 것이 직접적인 종료 조건이다.

같은 날 Chrome DevTools로 동일 매장의 실제 Mobiscroll 달력을 다시 확인했다. 기본 진입은 2026년 7월이며 월 제목, `Previous page`, `Next page`는 각각 보이는 요소가 하나뿐이었다. 정상 클릭에서는 다음과 같이 짧은 시간 안에 월 제목이 바뀌었다.

| 전환 | 월 제목 DOM 변경 |
|---|---:|
| 2026년 7월 -> 8월 | 약 24ms |
| 2026년 8월 -> 9월 | 약 44ms |

따라서 정상 월 전환이 10초 제한을 소진한 문제가 아니며, 실패 실행에서 첫 클릭이 유실된 뒤 adapter가 같은 월을 계속 기다린 것이 CSV와 라이브 DOM을 함께 설명하는 원인이다.

## 원인

`CalendarAdapter.prepareTarget()`은 월 이동을 한 번 수행하면 `pendingMonth`를 설정하고 표시 월이 바뀔 때까지 무기한 `waiting`을 반환한다. 전환 중 표시 월을 일시적으로 읽지 못하는 경우에도 pending 상태를 잃을 수 있다. 오케스트레이터는 50ms 간격으로 호출하지만 adapter에는 클릭 재시도 정책이 없었다.

## 변경

- 전환 중 표시 월이 `null`이면 기존 월 이동 pending을 유지한다.
- 750ms 동안 표시 월이 바뀌지 않으면 월 이동을 재시도한다.
- 동일 월 전환은 최대 3회 시도한다.
- 제한을 넘으면 10초까지 무의미하게 대기하지 않고 `blocked`로 인계한다.
- 표시 월이 실제로 다른 값이 되면 pending과 시도 횟수를 초기화하고 다음 월 이동을 진행한다.

이 변경은 예약 오픈 hot path가 아닌 초기 날짜 준비 단계에만 적용된다. 월 이동 버튼과 날짜 셀은 기존 DOM 판독·재조회 경계를 유지한다.

## 검증

- 월 이동 클릭이 무효화된 경우 bounded retry가 수행되는 단위 테스트
- 월 전환 중 월 제목이 잠시 사라지는 경우 pending을 유지하는 단위 테스트
- 기존 달력·Mobiscroll·오케스트레이터 회귀 테스트
- 실제 `bistropolpo` 달력에서 7월 -> 8월 -> 9월 월 제목 전환 확인
