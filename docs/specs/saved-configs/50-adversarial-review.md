# 설정 히스토리·즐겨찾기 적대적 리뷰

## 검토 항목

- 자동 히스토리 저장이 오픈런 시작을 지연시키는가
- 동시에 들어온 저장·삭제가 read-modify-write 경합으로 유실되는가
- 손상된 storage 데이터가 Side Panel 전체 렌더를 중단시키는가
- 같은 밀리초 저장이 ID 충돌을 일으키는가
- query가 다른 같은 식당 URL이 중복으로 쌓이는가
- 지난 설정 복원이 임의로 시각을 변경하거나 자동 실행하는가
- 저장 목록 20건이 Side Panel을 지나치게 길게 만드는가

## 리뷰 결과

1. **높음, 수정 완료:** 히스토리 쓰기를 `await`하면 예약 페이지 준비가 storage 지연만큼 늦어질 수 있었다. 직렬 큐에는 넣되 시작 경로에서는 기다리지 않게 변경했다.
2. **중간, 수정 완료:** 객체 모양만 확인한 손상 snapshot이 폼 복원 중 예외를 일으킬 수 있었다. 전체 설정 구조를 검증하고 실패 항목을 폐기한다.
3. **중간, 수정 완료:** 저장된 과거 fingerprint를 신뢰하면 규칙 변경이나 오염으로 중복 대체가 깨질 수 있었다. 조회 시 현재 규칙으로 다시 계산한다.
4. **낮음, 수정 완료:** 최대 20개 행이 열린 영역의 높이를 과도하게 늘렸다. 목록 높이를 제한하고 내부 스크롤을 적용했다.

저장 변경은 Background의 단일 직렬 큐를 통과하며 ID는 UUID를 사용한다. 복원은 폼 입력과 draft만 갱신하고 START 명령을 보내지 않는다. 치명적·높음 미해결 문제는 없다.
