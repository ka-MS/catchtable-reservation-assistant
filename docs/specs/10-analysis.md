# 10. 분석 - 실제 예약 플로우 확인

**상태:** passed  
**시작:** 2026-07-10
**최근 관찰:** 2026-07-10

## 목적

1차 어플리케이션이 지원할 단일 캐치테이블 예약 플로우를 실제 화면과 DOM 근거로 확정한다. 이 문서가 통과되기 전에는 실제 페이지 선택자나 클릭 순서를 구현하지 않는다.

## 현재 확인 사실

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| 공개 앱 루트 URL | 확인 | `https://app.catchtable.co.kr/`에 접근 가능 |
| 공개 식당 상세 URL | 확인 | `https://app.catchtable.co.kr/ct/shop/merry_go_round` 형식의 상세 URL을 확인 |
| 공개 화면의 예약 UI | 미확인 | 새 브라우저 세션에서 루트와 식당 상세 URL 모두 소셜 링크만 노출돼 예약 검색·날짜·인원·시간 슬롯을 관찰할 수 없었음 |
| 로그인 후 예약 흐름 | 확인 | 로그인된 Chrome에서 `kea` 식당의 시간 선택부터 결제 정보 입력 직전까지 관찰 |
| Chrome 사용자 세션 | 확인 | ChatGPT Chrome Extension을 통해 선택된 Chrome 탭에 연결됨 |
| 단일 지원 예약 플로우 | 확인 | 시간 슬롯, 조건부 테이블 타입, 예약금 안내, 결제 정보 입력 전 사용자 인계까지 확인 |

## 분석 결론

공개 식당 상세 URL은 일반 브라우저에서 예약 UI가 렌더링되지 않았지만, 로그인된 Chrome 탭에서는 실제 예약 흐름을 확인했다. `오후 12:00` 슬롯을 선택한 결과, 식당에 따라 나타날 수 있는 테이블 타입 선택, 예약금 안내, 결제 정보 입력 화면으로 순차 전환됐다.

예약금 안내의 `확인`은 결제 승인이 아니라 다음 결제 정보 화면으로 이동하는 단계다. 사용자가 이 단계를 진행하도록 명시적으로 허가했다. 반면 약관 동의와 `자동결제로 예약하기`는 외부 예약 및 결제 조건을 확정하므로 자동화의 종단 상태이며, 사용자에게 제어권을 넘겨야 한다.

## 관찰한 실제 예약 화면

관찰 URL:

```text
https://app.catchtable.co.kr/ct/shop/kea?type=DINING&personCount=2&date=260730
```

이 URL에서 다음을 확인했다.

- 매장명은 `케아`이며, 예약 영역의 선택 조건 버튼은 `07.30 (목) · 2명`으로 보인다.
- `예약` 섹션에는 `오후 12:00`, `오후 1:30`, `오후 6:00`, `오후 6:30`, `오후 7:00`, `오후 7:30`, `오후 8:00` 버튼이 실제로 표시됐다.
- 실제로 표시된 각 시간 버튼은 `<button>`이며 `aria-disabled="false"`, `data-busy="false"`를 가졌다.
- 화면에는 동일한 시간 버튼의 숨겨진 중복 DOM 노드도 존재했다. 따라서 시간 텍스트만으로는 안전하지 않고, 실제 표시 여부를 함께 검사해야 한다.
- 하단 고정 영역의 `예약하기` 버튼은 접근 가능한 이름 기준으로 단일 요소였다. 화면에는 `예약금 0원`, `자동결제` 조건도 표시된다.

## 시간 선택 뒤 실제 전이

관찰한 정상 전이는 다음과 같다.

```text
시간 슬롯 선택
  -> 로딩
  -> 테이블 타입 선택 (식당·슬롯에 따라 선택적)
  -> 예약금 안내
  -> 결제 정보 입력 전 화면 (사용자 인계)
```

- `테이블 타입 선택` 대화상자는 항상 나타나지 않는다. 관찰한 경우 `홀`, `룸`, `바` 라디오 선택지와 `다음` 버튼이 있었고, 일부 선택지는 비활성화될 수 있었다.
- 예약금 안내 대화상자는 `이전`, `확인` 버튼을 제공했다. 인원별 예약금과 환불 정책을 표시하며, `확인`을 누르면 결제 정보 입력 화면으로 이동했다.
- 결제 정보 입력 화면에는 약 6분의 예약 홀드 타이머, 예약 일시·인원·테이블 타입 요약, 약관 동의, 결제 방식 및 `자동결제로 예약하기` 최종 버튼이 있었다.
- 이 화면은 예약 완료가 아니다. 약관 동의나 최종 버튼은 자동 클릭하지 않고 `PAUSED_USER`로 전환해야 한다.
- 화면에 표시된 결제수단·카드 정보는 자동화 설정이나 진단 기록에 수집하거나 저장하지 않는다.

## 현재 DOM 판별 기준

| 대상 | 관찰된 기준 | 구현 전 판단 |
| --- | --- | --- |
| 대상 식당 | URL의 `/ct/shop/kea` 경로 | 식당 slug는 현재 단일 플로우 식별자 후보 |
| 날짜·인원 | 접근 가능한 이름 `07.30 (목) · 2명`의 단일 `button`과 URL의 `personCount`, `date` 파라미터 | URL 파라미터 형식의 일반화 여부는 추가 확인 필요 |
| 시간 슬롯 | `main` 내부의 `button[aria-disabled]` | 텍스트, 실제 표시 여부, `aria-disabled`를 함께 검사 |
| 슬롯 상태 | `aria-disabled="false"`, `data-busy="false"` | 예약 가능 여부와 정확히 같은 의미인지는 클릭 결과로 검증 필요 |
| 중복 노드 제거 | `getBoundingClientRect()`의 너비·높이가 모두 양수 | 현재 화면에서 7개 표시 슬롯으로 축소됨 |
| 예약 진입 | 접근 가능한 이름 `예약하기`의 단일 `button` | 현재 화면에서는 시간 슬롯 선택 뒤 자동 전이됐으며, 별도 버튼 역할은 추가 확인 필요 |
| 테이블 타입 | 접근 가능한 이름이 있는 대화상자의 `radio`와 `다음` 버튼 | 식당별 선택적 단계이므로 표시될 때만 처리 |
| 예약금 안내 | 대화상자 제목 `예약금 안내`, 단일 `확인` 버튼 | 다음 결제 정보 화면으로 가는 비최종 전이 |
| 사용자 인계 | 약관 동의 UI 또는 `자동결제로 예약하기` 최종 버튼 | 감시를 중지하고 결제·예약 확정을 사용자에게 인계 |
| 불안정한 기준 | `_12656hc0` 같은 해시 class | 선택자로 사용하지 않음 |

## 아직 확인하지 않은 전이

- 날짜·인원 조건 버튼을 눌렀을 때의 선택 UI와 URL/DOM 변화
- 슬롯 클릭 직후 자리가 소진된 실패 화면
- 로그인, CAPTCHA, 명시적 예약 완료 화면의 DOM 근거
- `예약하기` 버튼의 역할과 시간 슬롯 클릭과의 관계
- `data-busy` 값이 예약 가능/불가를 나타내는 정확한 규칙
- 테이블 타입 대화상자가 표시됐지만 사용자가 선호 테이블 타입을 지정하지 않은 경우의 정책

## 필요한 관찰 범위

아래 순서의 한 예약 플로우를 기준으로 관찰한다.

1. 식당 상세 또는 예약 진입 화면 - 확인
2. 날짜 선택
3. 인원 선택
4. 시간 슬롯 목록과 예약 가능/불가 상태 - 일부 확인
5. 시간 슬롯 클릭 뒤의 조건부 테이블 타입 및 예약금 안내 - 확인
6. 결제·수수료 확인처럼 자동화를 멈춰야 하는 화면 - 확인
7. 슬롯 소진, 로그인, CAPTCHA, 예약 완료 화면

각 단계에서 기록할 항목:

- 현재 URL과 SPA 이동 여부
- 사용자에게 보이는 텍스트와 버튼 역할
- 안정적인 `data-*`, ARIA, href, name 등 DOM 식별자
- 같은 슬롯이 재렌더링될 때 식별자가 유지되는지
- 다음 상태로 전환됐음을 증명하는 화면 신호

## 리스크

| ID | 리스크 | 대응 |
| --- | --- | --- |
| R1 | 로그인 전후 DOM이 달라 실제 선택자가 공개 화면과 맞지 않음 | 로그인된 실제 예약 화면만 구현 근거로 사용 |
| R2 | SPA 재렌더링으로 클릭 대상 노드가 교체됨 | 상태 전이와 단일 클릭 키를 실제 DOM 관찰 뒤 설계 |
| R3 | 예약 가능 상태가 별도 대기열/확인 화면과 혼동됨 | 각 화면의 명시적 성공·실패·사용자 확인 신호를 수집 |
| R4 | 결제 또는 수수료 확인을 예약 성공으로 오인함 | 사용자 확인 필요 상태를 별도 종단 상태로 정의 |
| R5 | 테이블 타입 대화상자를 모든 식당의 필수 단계로 가정함 | 대화상자 존재 여부를 먼저 판별하고, 미표시일 때는 다음 상태로 진행 |

## 분석 통과 조건

- 지원할 식당 예약 플로우 하나가 실제 화면 증거로 정해진다. - 충족
- 날짜, 인원, 시간 슬롯, 예약 가능, 사용자 확인 필요 화면의 DOM 식별 기준이 기록된다. - 충족
- 클릭 뒤 사용자 확인 필요 상태의 판별 기준이 기록된다. 슬롯 소진 실패 및 로그인/CAPTCHA는 보수적 미인식 처리와 모의 DOM 검증이 필요하다.
- 미확인 항목이 구현을 막지 않는 수준으로 축소된다. - 충족. 실패 신호는 확장된 자동화가 아니라 `PAUSED_USER` 또는 재감시로 처리한다.

## 다음 입력

설계 단계에서는 테이블 타입 선호가 설정되지 않았을 때의 동작을 결정한다. 민감한 계정 정보, 쿠키, 결제정보는 제공하거나 수집하지 않는다.
