# 오케스트레이터 확장성 기반

**상태:** 진행
**착수일:** 2026-08-07
**영역:** 실행 구조
**선행 패키지:** [오케스트레이터 리팩터링](../orchestrator-refactor/10-scope.md) (SP-009),
[Run control plane](../run-control-plane/20-design.md) (SP-020)

## 목표

`src/content/orchestrator.ts`가 오픈런 단일 흐름을 전제로 커진 구조를,
**동작을 바꾸지 않고** 단계적으로 분리한다. 새 예약 흐름을 추가할 때
기존 흐름의 제어 코드와 안전 계약을 건드리지 않아도 되는 상태를 만든다.

이 패키지는 **기반 작업만** 수행한다. 새 예약 흐름 자체는 구현하지 않는다.

## 배경

2026-08-07 사용자와의 구조 검토에서, 웨이팅·줄서기 같은 새 예약 흐름을
추가할 때 어디를 건드리게 되는지를 코드 수준에서 확인했다. 결론은
[10-analysis.md](10-analysis.md)에 측정값과 함께 기록했다. 요지는 다음과 같다.

- 코드베이스 전체는 과설계 상태가 아니다. 클래스 상속 0건, DI 컨테이너
  없음, 파일 중앙값 82줄이다. 총 12,501줄 중 흐름에 종속된 것은
  **35.6%** 이며, 나머지는 흐름과 무관하거나 공유되는 코드다.
- 문제는 한 곳에 있다. `orchestrator.ts` 1,630줄 안에서 **제어와 관측이
  섞여 있고**, 새 관측 기능이 들어올 때마다 이 파일만 자란다.
- 즉 증상은 과설계(over-abstraction)가 아니라 **과소설계(God file)** 이며,
  처방은 추상화를 걷어내는 것이 아니라 **경계(seam)를 추가**하는 것이다.

## 범위

| 단계 | 이름 | 내용 | 흐름 지식 | 게이트 |
|---|---|---|---|---|
| 01 | 관측 분리 | 제어와 관측 payload 조립을 분리한다 | 불필요 | 없음 |
| 02 | 커널·흐름 경계 | `RunSession`의 안전 계약을 흐름 정의와 분리한다 | 일부 | 없음 |
| 03 | 핫패스 전략 추출 | 핫패스를 자기 상태를 소유하는 단일 클래스로 뽑는다. 구현체는 오픈런 하나 | 불필요 | 없음 |
| 04 | 전략 일반화·흐름 선택 | 전략 인터페이스를 확정하고 흐름 선택 지점을 만든다 | 필요 | **있음** |

01~03은 **동작 무변경(behavior-neutral)** 이다. 이벤트 payload,
trace attribute, 타이밍 상수는 한 글자도 바꾸지 않는다.

### 03과 04를 나눈 이유

두 작업은 성격이 다르다. 초안에서는 하나로 묶여 있었고, 그 때문에
전체가 실측 게이트 대상으로 읽혔다.

**03은 추출이다.** 핫패스가 세션에서 쓰는 상태 8개는 전부 오픈런
전용이므로([10-analysis.md](10-analysis.md) §7), "전략이 자기 상태를
소유한다"는 원칙은 오픈런 하나만 보고도 도출된다. 새 흐름의 근거 없이
결정·검증할 수 있다.

다만 이 8개는 **핫패스(908~1212) 안에만 있지 않고** setup·핫패스 제어·
telemetry 소비·cleanup 네 곳에 걸쳐 있다. 따라서 03은 "핫패스 약 300줄
이동"이 아니라 그 경계까지 새로 긋는 작업이다. `advanceFromSlot`의 소속,
shadow listener 생명주기, `confirmPageReady`의 인접 날짜 확인 위치가
미결이며, **03의 정확한 범위는 01 완료 후 재측정으로 확정한다.**
telemetry 소비 지점 5곳이 01 이후 관측 계층 입력으로 바뀌어 표가
실질적으로 단순해지기 때문이다.

**04는 일반화다.** 위험은 최상위 시그니처(`run(ctx) => RunResult | null`)가
아니라 **커널이 전략에 넘기는 컨텍스트의 모양**에 있다. 구현체가 하나뿐인
상태에서 컨텍스트를 정의하면 `adjacentDate`·`toggleCycle` 같은 오픈런 전용
개념이 그 안에 들어가고, 두 번째 흐름이 오면 맞지 않아 다시 뜯게 된다.

## 04 진입 조건

다음을 **모두** 만족하기 전에는 04에 진입하지 않는다.

1. 01~03 완료 및 `main` 병합
2. **실측 근거가 있는 두 번째 예약 흐름의 spec 또는 evidence 확보**
   (`docs/analysis/site-behavior.md` 또는 `docs/evidence/` 에 해당 흐름의
   DOM·전이 관측이 존재할 것)

2번이 확보되지 않으면 이 패키지는 **03에서 완료 처리**한다. 04는 그때
해당 흐름 패키지로 이관하는 편이 나을 수 있으며, 이관 시 이 문서에
링크만 남긴다.

현재 웨이팅·줄서기의 실측 근거는 없다. 코드가 아는 것은
`EntryAdapter`가 읽는 "현장 웨이팅만 가능" 버튼 문자열 하나뿐이다
(`src/content/adapter/entry.ts:15`).

## 범위 밖

- **웨이팅·줄서기·취소 자리 감시 흐름의 구현.** 별도 패키지로 다룬다.
- `ReservationConfig`의 discriminated union 전환. 흐름 추가가 확정된 뒤
  해당 패키지에서 다룬다.
- `Dependencies` 포트 계약 변경, DOM 어댑터 수정, 준비 스테이지 엔진 수정.
- 새 trace code 추가, payload 값·이름·반올림 변경.
- 성능 개선. 이 패키지는 성능에 중립이며, 핫패스 상수를 만지지 않는다.

## 순서와 유동성

단계는 `01 → 02 → 03 → 04` 순서로 진행한다. 이 순서는 **뒤 단계의
작업량을 앞 단계가 줄이기 때문에** 정한 것이다. 01을 먼저 하면 03의
대상이 1,630줄에서 약 1,050줄로 줄어든다.

### 설계 문서를 미리 쓰지 않는 이유

`02`·`03`·`04`의 `20-design.md`는 **각 단계의 차례가 왔을 때 작성한다.**
지금 쓰면 앞 단계의 결과를 모르는 상태의 추측 설계가 된다
(`AGENTS.md` §1).

이 문서는 각 단계의 **순서·게이트·성공 기준만** 선언한다.

### 재평가 지점

각 단계가 `main`에 병합된 직후 다음을 판단하고, 결과를 이 문서의
`단계 상태`에 기록한다.

| 판단 | 조치 |
|---|---|
| 다음 단계의 전제가 유지되는가 | 유지되면 진행, 아니면 설계부터 다시 |
| 앞 단계가 예상보다 많은 것을 해결했는가 | 다음 단계의 범위를 축소하거나 취소 |
| 04 진입 조건 2번이 확보됐는가 | 미확보면 03에서 완료 처리 |

`02`와 `03`의 경계는 겹칠 수 있다. `confirmPageReady`의 인접 가용 날짜
확인은 오픈런 전용이지만 현재 공통 준비 단계 자리에 있다. 준비 단계에
남길지 전략으로 옮길지는 `02` 설계에서 정한다.

### 중단 조건

다음 중 하나라도 발생하면 그 단계에서 멈추고 사용자에게 보고한다.

- 동작 무변경을 유지한 채로는 목표 구조에 도달할 수 없다고 판명될 때
- 기존 테스트를 수정해야만 통과시킬 수 있을 때
  (= 경계를 잘못 그었다는 신호. 수정이 아니라 설계 재검토 대상)
- 핫패스 타이밍에 영향이 생길 때

### 단계별 단독 가치

각 단계는 뒤 단계의 완료를 전제하지 않는다. 어디서 멈춰도 그때까지의
결과가 `main`에서 유효하다.

- `01`만: `orchestrator.ts`가 1,630 → 약 1,050줄. 관측 로직이 단위
  테스트 가능해진다. 흐름 추가와 무관하게 이득이다.
- `+02`: 안전 계약(PIN 폐기 순서, terminal 단정 금지, cleanup 순서)이
  흐름 코드와 분리돼 복제 위험이 사라진다.
- `+03`: 오픈런 전용 상태와 핫패스 책임의 소유권이 커널에서 분리된다.
  커널에 커널만 남는다. 흐름 추가 계획이 사라져도 이득이다.
- `+04`: 새 흐름을 기존 흐름 수정 없이 추가할 수 있다.

## 성공 기준

01~03 공통이다.

1. **기존 테스트 무수정 통과** — `tests/orchestrator.test.mjs`(2,046줄)를
   포함한 전체 스위트를 수정하지 않고 통과한다.
2. **단계별 추가 검증** — 기존 테스트만으로는 동작 무변경을 기계적으로
   증명할 수 없다. `assert.deepEqual`은 값 비교이지 바이트 비교가 아니며
   키 순서를 검증하지 않고, `attributes` 객체 전체를 고정하는 단언은
   `CLOCK_SAMPLE` 하나뿐이다. 각 단계의 `20-design.md`가 그 단계에
   필요한 추가 테스트를 성공 기준에 명시한다.
3. `npm run check` 통과 (version·typecheck·test·dist·independence).
4. `git diff --check` 통과.
5. Chrome 수동 로드로 오픈런 1회 dry-run 정상 종료 확인.

## 브랜치와 병합

`docs/development/branch-strategy.md`의 기본 규칙을 따른다. 장기 브랜치는
사용하지 않는다.

| 순서 | 브랜치 | 담는 것 |
|---|---|---|
| 0 | `codex/docs-orchestrator-extensibility` | 이 문서, 10-analysis, 01/20-design, 카탈로그·HANDOFF 갱신 |
| 1 | `codex/refactor-observation-split` | 01 코드 + 01/30-implementation + 01/40-verification |
| 2 | `codex/refactor-kernel-flow-boundary` | 02/20-design + 코드 + 30/40 |
| 3 | `codex/refactor-hot-path-extraction` | 03/20-design + 코드 + 30/40 |
| 4 | `codex/refactor-flow-selection` | 04/20-design + 코드 + 30/40 (게이트 통과 시) |

각 브랜치는 **직전 브랜치가 `main`에 병합된 뒤** 최신 `main`에서 만든다.
병합 후 HANDOFF를 갱신한다.

장기 브랜치를 쓰지 않는 이유는 각 단계의 중간 상태가 배포 가능하기
때문이다. 격리 이득이 없는 반면, `orchestrator.ts`는 최근에도 실측 기반
수정이 들어오는 파일(`#16`, `#18`)이라 장기 분기의 충돌 비용만 남는다.

다음 조건이 발생하면 장기 브랜치로 전환을 재검토한다.

- 중간에 테스트가 깨지는 구간이 불가피하다고 판명될 때
- 뒤 단계의 설계가 앞 단계 결과에 따라 크게 흔들려 단계를 왕복해야 할 때

## 릴리스 영향

01~04는 모두 `refactor:` 커밋이다. Release Please 기본 설정에서
`refactor:`는 changelog에 노출되지 않고 버전도 올리지 않는다. 따라서
이 패키지만으로는 **릴리스 PR이 생성되지 않는다.** 의도된 동작이다.
빌드 ZIP이 필요하면 별도로 판단한다.
