# 오케스트레이터 확장성 기반

**상태:** 진행
**착수일:** 2026-08-07
**영역:** 실행 구조
**선행 패키지:** [오케스트레이터 리팩터링](../orchestrator-refactor/10-scope.md) (SP-009),
[Run control plane](../run-control-plane/20-design.md) (SP-020)

## 목표

`src/content/orchestrator.ts`가 오픈런 단일 흐름을 전제로 커진 구조를,
**동작을 바꾸지 않고** 세 단계에 걸쳐 분리한다. 새 예약 흐름을 추가할 때
기존 흐름의 제어 코드와 안전 계약을 건드리지 않아도 되는 상태를 만든다.

이 패키지는 **기반 작업만** 수행한다. 새 예약 흐름 자체는 구현하지 않는다.

## 배경

2026-08-07 사용자와의 구조 검토에서, 웨이팅·줄서기 같은 새 예약 흐름을
추가할 때 어디를 건드리게 되는지를 코드 수준에서 확인했다. 결론은
[10-analysis.md](10-analysis.md)에 측정값과 함께 기록했다. 요지는 다음과 같다.

- 코드베이스 전체는 과설계 상태가 아니다. 상속 0건, DI 컨테이너 없음,
  파일 중앙값 83줄이다. 총량 12,501줄 중 **64%는 흐름 수와 무관한 고정비**
  (MV3 복구, 관측·진단, 서버시계, XHR shadow, UI)다.
- 문제는 한 곳에 있다. `orchestrator.ts` 1,630줄 안에서 **제어와 관측이
  섞여 있고**, 새 관측 기능이 들어올 때마다 이 파일만 자란다.
- 즉 증상은 과설계(over-abstraction)가 아니라 **과소설계(God file)** 이며,
  처방은 추상화를 걷어내는 것이 아니라 **경계(seam)를 하나 추가**하는 것이다.

## 범위

| 단계 | 이름 | 내용 | 흐름 지식 필요 |
|---|---|---|---|
| 01 | 관측 분리 | 제어와 관측 payload 조립을 분리한다 | 불필요 |
| 02 | 커널·흐름 경계 | `RunSession`의 안전 계약을 흐름 정의와 분리한다 | 일부 |
| 03 | 실행 전략 교체 | 핫패스를 교체 가능한 실행 전략으로 만든다 | 필요 |

세 단계 모두 **동작 무변경(behavior-neutral)** 이다. 이벤트 payload,
trace attribute, 타이밍 상수는 한 글자도 바꾸지 않는다.

## 범위 밖

- **웨이팅·줄서기·취소 자리 감시 흐름의 구현.** 별도 패키지로 다룬다.
  해당 흐름은 실사이트 실측 근거가 아직 없다
  (`docs/analysis/site-behavior.md`에 관련 관측 없음).
- `ReservationConfig`의 discriminated union 전환. 흐름 추가가 확정된 뒤
  해당 패키지에서 다룬다.
- `Dependencies` 포트 계약 변경, DOM 어댑터 수정, 준비 스테이지 엔진 수정.
- 새 trace code 추가, payload 값·이름·반올림 변경.
- 성능 개선. 이 패키지는 성능에 중립이며, 핫패스 상수를 만지지 않는다.

## 순서와 유동성

단계는 `01 → 02 → 03` 순서로 진행한다. 이 순서는 **뒤 단계의 작업량을
앞 단계가 줄이기 때문에** 정한 것이다. 01을 먼저 하면 03의 교체 대상이
1,630줄에서 약 1,050줄로 줄어든다.

### 설계 문서를 미리 쓰지 않는 이유

`02`와 `03`의 `20-design.md`는 **각 단계의 차례가 왔을 때 작성한다.**
지금 쓰면 앞 단계의 결과를 모르는 상태의 추측 설계가 된다
(`AGENTS.md` §1). 특히 `03`의 실행 전략 인터페이스 시그니처는 새 흐름의
핫패스가 어떻게 생겼는지에 크게 의존하므로, 실측 없이 확정하지 않는다.

이 문서는 세 단계의 **순서와 성공 기준만** 선언한다.

### 재평가 지점

각 단계가 `main`에 병합된 직후 다음을 판단하고, 결과를 이 문서의
`단계 상태`에 기록한다.

| 판단 | 조치 |
|---|---|
| 다음 단계의 전제가 유지되는가 | 유지되면 진행, 아니면 설계부터 다시 |
| 앞 단계가 예상보다 많은 것을 해결했는가 | 다음 단계의 범위를 축소하거나 취소 |
| 새 흐름 추가 계획이 사라졌는가 | `03` 취소. `01`·`02`만으로도 단독 가치가 있다 |

### 중단 조건

다음 중 하나라도 발생하면 그 단계에서 멈추고 사용자에게 보고한다.

- 동작 무변경을 유지한 채로는 목표 구조에 도달할 수 없다고 판명될 때
- `tests/orchestrator.test.mjs`를 수정해야만 통과시킬 수 있을 때
  (= 경계를 잘못 그었다는 신호. 수정이 아니라 설계 재검토 대상)
- 핫패스 타이밍에 영향이 생길 때

### 단계별 단독 가치

세 단계는 서로의 완료를 전제하지 않는다. 어디서 멈춰도 그때까지의
결과가 `main`에서 유효하다.

- `01`만: `orchestrator.ts`가 1,630 → 약 1,050줄. 관측 로직이 단위
  테스트 가능해진다. 흐름 추가와 무관하게 이득이다.
- `01`+`02`: 안전 계약(PIN 폐기 순서, terminal 단정 금지, cleanup 순서)이
  흐름 코드와 분리돼 복제 위험이 사라진다.
- `01`+`02`+`03`: 새 흐름을 기존 흐름 수정 없이 추가할 수 있다.

## 성공 기준

전 단계 공통이다.

1. `tests/orchestrator.test.mjs`(2,046줄)를 **한 줄도 수정하지 않고** 통과.
   이 테스트는 trace attribute를 `assert.deepEqual`로 검증하므로, payload가
   한 글자라도 바뀌면 실패한다. 동작 무변경의 기계적 증명으로 사용한다.
2. `npm run check` 통과 (version·typecheck·test·dist·independence).
3. `git diff --check` 통과.
4. Chrome 수동 로드로 오픈런 1회 dry-run 정상 종료 확인.

`SP-009` 오케스트레이터 리팩터링에서 사용한 기준과 동일하다.

## 브랜치와 병합

`docs/development/branch-strategy.md`의 기본 규칙을 따른다. 장기 브랜치는
사용하지 않는다.

| 순서 | 브랜치 | 담는 것 |
|---|---|---|
| 0 | `codex/docs-orchestrator-extensibility` | 이 문서, 10-analysis, 01/20-design, 카탈로그·HANDOFF 갱신 |
| 1 | `codex/refactor-observation-split` | 01 코드 + 01/30-implementation + 01/40-verification |
| 2 | `codex/refactor-kernel-flow-boundary` | 02/20-design + 코드 + 30/40 |
| 3 | `codex/refactor-execution-strategy` | 03/20-design + 코드 + 30/40 |

각 브랜치는 **직전 브랜치가 `main`에 병합된 뒤** 최신 `main`에서 만든다.
병합 후 HANDOFF를 갱신한다.

장기 브랜치를 쓰지 않는 이유는 세 단계의 중간 상태가 전부 배포 가능하기
때문이다. 격리 이득이 없는 반면, `orchestrator.ts`는 최근에도 실측 기반
수정이 들어오는 파일(`#16`, `#18`)이라 장기 분기의 충돌 비용만 남는다.

다음 조건이 발생하면 장기 브랜치로 전환을 재검토한다.

- 중간에 테스트가 깨지는 구간이 불가피하다고 판명될 때
- `03`의 설계가 `01`·`02`의 결과에 따라 크게 흔들려 세 단계를 왕복해야 할 때

## 릴리스 영향

세 단계 모두 `refactor:` 커밋이다. Release Please 기본 설정에서
`refactor:`는 changelog에 노출되지 않고 버전도 올리지 않는다. 따라서
이 패키지만으로는 **릴리스 PR이 생성되지 않는다.** 의도된 동작이다.
빌드 ZIP이 필요하면 별도로 판단한다.
