# 에이전트 작업 방식과 트러블슈팅 기록

**상태:** 기록
**기간:** 2026-08-06 ~ 2026-08-07
**부모 패키지:** [오케스트레이터 확장성 기반](00-index.md)

> 이 문서는 SP-025 작업의 **산출물이 아니라 과정**을 남긴다. 제품 기준이
> 아니므로 다른 문서가 이 문서를 근거로 삼지 않는다. 나중에 문서 체계
> 바깥(예: 개발 가이드)으로 옮길 것을 전제로, 이 패키지를 몰라도 읽히게
> 자족적으로 썼다.

---

## 1. 누가 썼나

Claude Code에서 동작하는 에이전트(Claude Opus 5)가 사용자와 대화하며
작업했다. 사람이 방향과 결정을 쥐고, 에이전트가 측정·설계·구현·문서화를
수행하는 형태다.

작업 조건은 다음과 같았다.

- `AGENTS.md`가 공통 행동 기준이다. 특히 §1(가정하지 않기, 혼란을 드러내기),
  §2(단순함 우선), §3(외과적 변경), §5(단계 전환 전 HANDOFF 확인)가
  이 작업의 판단에 반복해서 개입했다.
- 사이트 동작은 실측 근거 없이 추측 구현하지 않는다.
- `docs/specs/` 패키지 규약(10-analysis → 20-design → 30-implementation →
  40-verification)을 따른다.
- 사용자는 코드 리뷰를 직접 수행했다. 이 문서에 나오는 지적은
  PR [#19](https://github.com/ka-MS/catchtable-reservation-assistant/pull/19)(문서)와
  [#21](https://github.com/ka-MS/catchtable-reservation-assistant/pull/21)(코드)의
  실제 리뷰다.

작업의 시작은 기능 요청이 아니라 **질문**이었다. "웨이팅·줄서기를 추가하면
기존 코드를 얼마나 건드리게 되나, 플러그인처럼 붙일 수 있나."

## 2. 무엇을 반복해서 틀렸나

이 작업에서 다섯 번 사실을 틀렸다. **전부 같은 구조였다.**

(성격이 다른 실패가 하나 더 있다 — 검사 축을 잘못 골라 실제 코드 회귀를
놓친 건이다. 문서 서술이 아니라 검증 설계의 문제라 §3에서 따로 다룬다.)

| # | 틀린 서술 | 실제 | 누가 잡았나 |
|---|---|---|---|
| 1 | "총량의 64%가 흐름 무관 고정비" | 같은 표에서 UI·설정을 "거의 불변/소폭 증가"로 분류해놓고 전부 고정비로 합산. 3분할이 맞다 | 리뷰어 |
| 2 | "8개 필드는 핫패스 밖에서 쓰이지 않는다" | 바로 위 표에 `1224`·`1225`·`1270`·`475`·`502`를 내가 직접 적어놨다 | 리뷰어 |
| 3 | "관측 전용 catch 9 → 1" | 바로 앞에 fallback이 5종이라고 써놓고 1로 합칠 수 있다고 함 | 리뷰어 |
| 4 | "trace가 던지면 `start()`가 reject" | 실제로는 `FAILED` 종결. reject는 `emit`이 던질 때만 | 에이전트(테스트 작성 중) |
| 5 | "25ms 루프 안에 관측이 없다" | `applyPendingEmptyExit` → `traceAvailabilityEmptyExit`가 루프 안에 있다 | 에이전트(성공 기준 8 실행 중) |

측정값 자체가 틀린 경우도 있었다(`class/interface` 34/147 → 34/150,
평균 152 → 150.6). 이건 성격이 다르다 — 합계는 `wc -l`로 세고 평균만
`split("\n").length`로 세서 생긴 계산 불일치였다.

### 공통 구조

**데이터는 맞는데, 그 데이터를 요약한 문장이 틀렸다.**

순서가 항상 같았다. 측정하고 → 표를 만들고 → 그 위에 요약 문장을 쓴다.
요약을 쓸 때 표를 다시 보지 않는다. 그래서 표에는 예외가 적혀 있는데
요약에는 없다.

그리고 **요약이 깔끔할수록 틀릴 확률이 높았다.** `64%`, `0`, `1`,
"쓰이지 않는다", "없다" — 전부 예외를 지워야 나오는 형태다. 예외를
지우면 문장이 좋아지므로, 문장을 좋게 만들려는 힘이 곧 사실을 왜곡하는
힘으로 작동했다.

### 왜 이게 위험한가

이 오류들은 **자기 검증을 통과한다.** 표가 옆에 있으니 근거가 있어
보이고, 실제로 근거의 90%는 맞다. 틀린 건 마지막 한 문장인데, 나중에
읽는 사람은 표가 아니라 그 문장을 인용한다.

3번이 특히 그랬다. `9 → 1`이 설계 문서의 "예상 결과" 표에 들어가 있었고,
그대로 구현했다면 `trace`·`breadcrumb`·페이지 캡처·snapshot·
`diagnostics.failure`의 서로 다른 fallback이 하나로 뭉개졌을 것이다.

## 3. 무엇이 그걸 잡았나

1~3번은 사람이 잡았고 4~5번은 에이전트가 잡았다. **4~5번은 우연이 아니다.**

- **4번**: "기존 테스트만으로는 payload 무변경을 증명할 수 없으니 특성화
  테스트를 먼저 쓴다"는 성공 기준 때문에 잡혔다. 테스트를 쓰려면 기대값을
  써야 하고, 기대값을 쓰려면 실제로 돌려봐야 한다. `assert.rejects`가
  실패하면서 드러났다.
- **5번**: 성공 기준 8("이 11개 행이 안 바뀌었는지, 이 루프에 관측이
  추가되지 않았는지 확인한다") 때문에 잡혔다. 확인하려고 루프를 grep 했더니
  1건이 나왔다.

### 실행 가능한 형태로 바꾸면 자기가 잡는다

원래 에이전트가 제안했던 문장은 이랬다.

> "리뷰 시 주석·문서와 실제 코드를 대조하는 항목을 명시적으로 넣는 게
> 좋겠습니다."

사용자가 되물었다. **"이 문구를 어디다 넣겠단 거임?"**

이 질문이 핵심이었다. 넣을 자리가 없었다. 범용 체크리스트에 넣으면
읽히지 않고 체크된다. 실제로 리뷰어가 오류를 잡은 방식은 체크리스트가
아니라 **표의 행 번호와 요약 문장을 직접 대조**한 것이었다.

그래서 형태를 바꿨다.

```markdown
8. 주장 대조 — 테스트로 고정되지 않는 두 주장을 diff에서 직접 확인한다.
   (a) 제어 복원력 catch 11개(271·435·472·479·725·730·869·913·1035·
       1173·1377)가 변경되지 않았을 것
   (b) runToggleCycle 스캔 루프의 매 반복 경로에 observer 호출이
       추가되지 않았을 것
```

"대조하라"가 아니라 **"이 11개 행을 보라"** 다. 대상이 지정되면 실행할 수
있고, 실행하면 결과가 나온다. 5번은 이 항목을 실행한 결과다.

교훈: **검증 항목은 동사가 아니라 대상으로 쓴다.**

### 그런데 대상을 잘못 고르면 그대로 통과한다

이 교훈에는 후속편이 있다. 성공 기준 8을 만들고 매 커밋마다 실행했는데도
**실제 회귀를 놓쳤다.**

관측 계층을 만들면서 격리 헬퍼를 이렇게 썼다.

```ts
private sendSafe(code, severity, message, options): void {
  this.safeCall(() => this.send(code, severity, message, options), undefined);
}
```

호출부는 이렇다.

```ts
this.sendSafe("CLOCK_SAMPLE", "trace", msg, {
  serverAt: this.ctx.serverAt(),   // ← safeCall 밖에서 평가된다
  state: null,
  attributes: {...},
});
```

**options 객체가 호출 전에 평가되므로 `ctx.serverAt()` 예외는 경계 밖으로
샌다.** 이동 전에는 스탬핑 계산까지 `try` 안에 있었으니 경계가 좁아진
것이다. 설계 문서 원칙 1에 "현재의 예외 격리 동작을 한 곳도 바꾸지
않는다"고 적어놓고 정작 그걸 어겼다.

`clockSamples()`는 `execute()`의 `finally`에서 호출되므로, 던지면 terminal
`RunResult`를 덮고 flush까지 건너뛴다.

### 왜 성공 기준 8이 못 잡았나

기준 8(a)은 이렇게 적혀 있었다.

> 제어 복원력 `catch` 11개(271·435·…)가 변경되지 않았을 것

매 커밋마다 실행했고 **11/11 통과했다.** 그런데 바뀐 것은 `catch`의
**개수**가 아니라 **경계의 범위**였다. 검사 축이 달랐다.

- 내가 검사한 축: `try/catch` 블록이 몇 개인가
- 실제로 바뀐 축: 어떤 표현식이 그 블록 **안에** 있는가

개수는 **대리 지표(proxy)** 다. 대리 지표와 실제 속성이 어긋나는 순간,
검사는 통과하고 속성은 깨진다. 그리고 `11/11`은 §2에서 말한 "깔끔한
요약"의 전형이다 — 깨끗한 숫자가 근거 없는 안심을 준다.

### 대상을 고르는 법

"이 11개 행을 보라"는 실행 가능해서 좋았지만, **대상을 고르는 단계가
빠져 있었다.** 순서를 하나 앞에 둬야 한다.

1. **이 변경에서 바뀔 수 있는 축이 무엇인가**를 먼저 적는다
2. 그 축을 직접 재는 검사를 만든다
3. 검사를 실행 가능한 대상 형태로 쓴다

이번 경우 1번의 답은 "코드를 헬퍼로 옮기면 **평가 시점**이 바뀔 수 있다"
였다. 그러면 검사는 개수 세기가 아니라 **"경계 안에서 던지게 만들어
보기"** 가 된다.

실제로 그렇게 확인했다. 던지는 컨텍스트를 주입하니 두 메서드가 바로
드러났다.

```
preparation()    ✅ 격리됨
wakeResult()     ❌ 전파됨: serverAt boom
emptyExit()      ✅ 격리됨
clockSamples()   ❌ 전파됨: serverAt boom
```

이 실험을 그대로 테스트로 옮겼다(`observation-run-observer.test.mjs`).
개수를 세는 검사는 사람이 매번 돌려야 하지만, 축을 직접 재는 검사는
테스트가 되어 영구히 남는다.

교훈: **셀 수 있다고 그게 검사할 축인 것은 아니다.** 개수·존재 여부처럼
자동화하기 쉬운 지표에 먼저 손이 가는데, 그건 대개 대리 지표다. 검사를
만들기 전에 "이 변경이 무엇을 바꿀 수 있는가"를 한 줄 적는다.

## 4. 루프 계약 — 틀린 규칙은 규칙 전체를 죽인다

5번을 고칠 때 표면적 수정은 간단했다. "루프 안에 관측이 없다" →
"매 반복 경로에 관측이 없다". 하지만 이건 문구 수정이 아니라 **계약의
성립 여부**였다.

원래 문구대로 코드에 주석을 달았다면 이렇게 됐을 것이다.

```ts
// 이 루프 안에 관측을 넣지 않는다.
while (...) {
  candidate = inspectSlots();
  ...
  const emptyExit = applyPendingEmptyExit();   // ← 내부에서 trace를 호출한다
```

주석과 바로 아래 코드가 모순된다. 이 주석을 읽는 다음 사람의 반응은
"주석이 틀렸네"이고, 그 순간 **주석 전체가 신뢰를 잃는다.** 지키라고 쓴
규칙이 무시되는 규칙이 된다.

실제로 넣은 주석은 이렇다.

```ts
// 관측 계약(SP-025/01): 이 루프의 **매 반복 경로**에는 관측 호출을 넣지
// 않는다. 25ms·10ms 간격으로 도는 슬롯 감지 구간이다. 종료가 확정된
// 직후의 1회 관측(applyPendingEmptyExit 내부, EMPTY_EARLY_EXIT)은
// 허용된다 — 실행 즉시 break 하거나 return 하므로 반복 비용에 누적되지
// 않는다.
```

길지만 코드와 일치한다. 예외를 명시하고 **왜 예외인지**(즉시 벗어나므로
누적되지 않음)까지 적어서, 새 관측을 추가하려는 사람이 자기 경우가
예외에 해당하는지 판단할 수 있다.

교훈: **예외를 지운 깔끔한 규칙보다, 예외를 품은 정확한 규칙이 오래
산다.** 전자는 첫 반례에서 죽고 후자는 판단 기준으로 남는다.

## 5. 리팩터에 버그 수정을 섞지 않았다

작업 중 두 번, 고칠 수 있는 문제를 발견하고 고치지 않았다.

**(1) `catch` 22개가 전부 관측용이 아니었다**

설계는 "관측 격리용 22개를 하나로 합친다"였는데, 분류해보니 관측 9 /
혼합 2 / **제어 복원력 11**이었다. `availabilityWake.wait` 실패 시
`deps.sleep`으로 넘어가는 핫패스 폴백, `attemptPhase` control plane 신호,
`new URL()` 파싱 실패 처리가 섞여 있었다.

→ 제어 11개는 손대지 않는 것으로 범위를 좁혔다.

**(2) 관측 예외 격리가 비대칭이었다**

`trace` 호출 10곳 중 6곳만 격리돼 있었다. 나머지 4곳에서 exporter가
던지면 실행이 `FAILED`로 죽는다. `emit`은 더 나빠서 `RunResult` 자체가
반환되지 않아 attempt 종결 보고까지 막힌다.

명백한 개선 여지였지만 **고치지 않고 그대로 보존했다.** 대신
`RunObserver`에 `send()`(전파)와 `sendSafe()`(격리)를 나눠 두어 비대칭이
호출부에서 보이게 만들고, 판단은
[issue #20](https://github.com/ka-MS/catchtable-reservation-assistant/issues/20)으로
분리했다.

### 왜 참았나

이유는 두 가지다.

1. **회귀 시 원인 분리가 불가능해진다.** 구조 분리와 동작 변경을 한
   커밋에 섞으면, 나중에 문제가 났을 때 구조 때문인지 격리 변경 때문인지
   가릴 수 없다. 이 코드는 예약 오픈 순간에 ms 단위로 도는 코드다.
2. **"전부 삼키는 게 옳은가"가 자명하지 않다.** trace exporter가 OOM으로
   던지는 상황이라면 조용히 계속 진행하는 쪽이 더 위험할 수도 있다.
   판단이 필요한 사안을 리팩터에 묻어서 처리하면 아무도 판단하지 않은 채
   결정된다.

부수 효과가 하나 생겼다. 01이 끝나면 **지금은 우연인 비대칭이 코드에
명시된다.** 어느 관측이 실행을 죽일 수 있는지가 `send`/`sendSafe` 호출로
드러나므로, #20을 판단할 때 근거가 이미 코드에 있다. 고치지 않은 것이
고칠 준비가 됐다.

## 6. 감으로 답할 뻔한 질문을 측정으로 답했다

작업의 분기점은 사용자의 이 말이었다.

> "1흐름에 84파일 12.5k줄이라고 하니 과한 뭔가가 생긴 게 아닌가 싶기도
> 하고. 뭔가 잘못된 걸까?"

여기서 "구조는 괜찮습니다" 또는 "네 좀 복잡하네요" 중 아무거나 답할 수
있었고, 둘 다 근거가 없었다. 대신 셌다.

```
클래스 상속        0건        ← 검출된 8건은 전부 제네릭 제약
DI 컨테이너        없음
파일 중앙값        82줄
흐름 종속 코드     35.6%      ← 나머지는 흐름 무관하거나 공유
orchestrator.ts    354줄이 payload 조립 (파일의 22%)
```

결론이 뒤집혔다. **과설계가 아니라 과소설계**였다. 이 구분이 중요한 이유는
증상이 같고 처방이 정반대이기 때문이다.

| | 증상 | 처방 |
|---|---|---|
| 과설계 | 얇은 파일 다수, 호출 추적 어려움, 죽은 인터페이스 | 걷어내기 |
| 과소설계 | God file, 한 파일이 계속 자람 | **seam 추가** |

둘 다 "구조가 잘 안 된다"고 느껴진다. 여기서 감으로 "과설계인 것 같다"고
답했다면 추상화를 제거하는 방향으로 갔을 것이고, 정확히 반대 방향이다.

교훈: **"이거 과한가"라는 질문에는 세어서 답한다.** 줄 수로는 판단할 수
없고(도메인이 어려우면 코드는 원래 길다), 다음 세 가지를 본다.

1. 기능 하나 추가에 건드리는 파일 수
2. 실제로 교체된 적 있는 인터페이스인가 (테스트에서라도)
3. "이 파일을 지우면 제품이 무엇을 잃는가"에 답할 수 있는가

## 7. 실제로 효과가 있었던 작업 순서

### 추출 전에 현재 동작을 테스트로 박는다

커밋 0이 코드 변경 없이 테스트만 21개 추가하는 커밋이었다. 이게 없었으면
이후 추출의 안전망이 기존 테스트뿐이었을 텐데, 기존 테스트는 부족했다.

- `attributes` 객체 **전체**를 고정하는 단언은 561개 중 하나뿐이었다
- `assert.deepEqual`은 값 비교이지 키 순서를 보지 않는다
- 예외 격리 동작과 호출 순서는 아무도 검증하지 않았다

즉 "기존 테스트 무수정 통과"는 **필요조건이지 충분조건이 아니었다.**
사용자 리뷰가 정확히 이 점을 지적했고, 그래서 커밋 0이 생겼다.

### 기대값을 추측하지 않고 덤프해서 확보한다

특성화 테스트의 기대값을 손으로 쓰면 그 자체가 추측이다. 대신 스크립트로
실행해 모든 이벤트·trace를 JSON으로 덤프한 뒤, 그 값을 테스트에 옮겼다.
4번 오류가 여기서 드러났다.

### 키 순서까지 고정한다

```js
function pinPayload(actual, expected) {
  assert.deepStrictEqual(actual, expected);
  assert.deepStrictEqual(Object.keys(actual), Object.keys(expected), "키 순서가 바뀌었습니다");
}
```

`deepEqual`만으로는 객체 리터럴이 재구성돼도 통과한다. 리팩터가 "값은
같은데 구조를 바꿨다"를 잡으려면 별도 단언이 필요하다.

### 커밋을 되돌리기 쉬운 순서로 쪼갠다

```
0  테스트만 추가        위험 0
1  순수 함수 이동       위험 거의 0
2  RunObserver 도입     핵심
3  breadcrumb 정책 이동
4  제어·관측 분할       가장 까다로움
```

각 커밋이 독립적으로 `npm run check` 그린이다. 중간에 멈춰도 손해가 없고,
문제가 나면 어느 커밋인지 바로 좁혀진다.

## 8. 사용자 개입이 결정적이었던 지점

에이전트가 혼자 갔으면 틀렸을 곳들이다. 기록해 둘 가치가 있다.

**"03은 패턴 변경만 하는 것 같은데 실측이 왜 필요함?"**

리뷰가 "Phase 03은 실측 게이트가 필요하다"고 했고 에이전트는 수긍했다.
사용자가 되물었고, 다시 보니 03에 성격이 다른 두 작업이 묶여 있었다.
추출(오픈런 코드만으로 결정 가능)과 일반화(두 번째 흐름 필요). 게이트는
후자에만 필요했다. → 03/04로 분리.

에이전트는 리뷰어의 지적을 받아들이는 쪽으로 기울었고, 그 지적이 **에이전트
자신의 문서를 인용한 것**이라는 점을 놓쳤다. 문서가 틀렸으면 그걸 근거로 한
지적도 재검토 대상이다.

**"그럼 03 04로 나누면 되는 거 아님?"**

에이전트는 `03a`/`03b` 하위 라벨을 제안했다. 사용자가 단순한 답을 냈고
그게 맞았다 — 게이트가 다르면 단계가 다르고, spec 디렉터리가 이미 숫자
접두사라 규약에도 맞는다.

**"이 문구를 어디다 넣겠단 거임?"**

3절에 적은 그 질문이다. 모호한 제안을 실행 가능한 항목으로 바꾼 계기다.

**"이 문제를 git issue로 올리는 건 어떨까?"**

에이전트는 "별도 `fix:` 브랜치로 분리"까지만 생각했다. 판단이 필요한
사안은 브랜치가 아니라 이슈로 남겨야 근거와 선택지가 보존된다.

패턴이 보인다. **사용자의 개입은 대부분 "그 결론이 정말 그 근거에서
나오나"를 되묻는 형태였다.** 새 정보를 준 게 아니라, 에이전트가 이미 가진
정보를 다시 보게 했다.

## 9. 남길 것

이 작업에서 재사용할 만한 것만 추린다.

1. **"이거 과한가"에는 세어서 답한다.** 과설계와 과소설계는 체감이 같고
   처방이 반대다.
2. **검증 항목은 동사가 아니라 대상으로 쓴다.** "대조하라"가 아니라
   "이 11개 행을 보라".
3. **대상을 고르기 전에 "이 변경이 무엇을 바꿀 수 있는가"를 한 줄 적는다.**
   개수·존재 여부는 자동화하기 쉬워서 먼저 손이 가지만 대개 대리 지표다.
   실제로 바뀌는 축을 직접 재야 한다. 셀 수 있다고 그게 검사할 축은 아니다.
4. **예외를 품은 정확한 규칙이 예외를 지운 깔끔한 규칙보다 오래 산다.**
   틀린 계약은 계약 전체의 신뢰를 죽인다.
5. **요약 문장은 표를 다시 보면서 쓴다.** 데이터가 맞아도 요약이 틀리면
   인용되는 건 요약이다. 특히 `0`·`1`·"없다"·"전부" 같은 형태를 쓸 때
   한 번 더 확인한다.
6. **리팩터에 버그 수정을 섞지 않는다.** 판단이 필요한 사안을 리팩터에
   묻으면 아무도 판단하지 않은 채 결정된다. 이슈로 분리한다.
7. **추출 전에 현재 동작을 테스트로 박고, 기대값은 덤프해서 확보한다.**
8. **커밋은 되돌리기 쉬운 순서로.** 테스트 → 순수 이동 → 구조 → 분할.
