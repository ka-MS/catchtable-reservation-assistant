# XHR 슬롯 응답 감시 — 분석·설계·구현 계획

**기준일:** 2026-07-12
**선행:** 시계 노이즈 해소(worklog 11). openDelta가 실런 간 비교 가능해짐.
**상태:** 설계 초안. **§2 실측 정찰 완료 전 구현 착수 금지(실측 원칙).**

## 1. 문제 분석 (현행 감지 메커니즘의 구조적 한계)

현재 감지 경로: 인접 날짜 클릭 → 목표 날짜 클릭 → (SPA가 슬롯 XHR 발사) → 응답 도착 → 렌더 → DOM 스캔.

orchestrator의 `runToggleCycle` 구조상 스캔이 허용되는 창은:

- 목표 클릭 후 고정 20ms sleep + 날짜 선택 확인 폴링(최대 60ms) **이후부터**
- **다음 사이클의 인접 클릭 시각(목표−40ms)까지만**

토글 간격 150ms 기준 실제 스캔 창은 사이클당 수십 ms다. 반면 슬롯 XHR 왕복은 ~100-200ms라, 클릭 N의 응답은 대부분 클릭 N의 스캔 창이 닫힌 뒤(= 인접 날짜 표시 중인 블라인드 구간이거나 다음 사이클 대기 중)에 도착한다. 결과: **감지가 "오픈 통과 첫 클릭 + 1~3사이클"로 양자화**된다. 진짜 오픈런에서는 +200~450ms 감지가 구조적 바닥이다.

목표: 감지 시각 ≈ 응답 도착 + 렌더 지연. 오픈 직후 클릭의 응답(+RTT ~100-200ms)을 즉시 잡으면 이론상 +100~250ms → 클릭까지 포함해 현행 대비 1~2사이클(150~300ms) 단축.

|---|---|---|
| R1 | 슬롯 목록 XHR의 URL 패턴·메서드 (날짜 토글 시 DevTools Network, 매장 2곳 교차) | 감시 필터 셀렉터 |

## 3. 설계

### 방식 비교

| 방식 | 바디 | 침습성 | 평가 |
|---|---|---|---|
| **A. PerformanceObserver 리소스 타이밍** | 없음(도착 시각·URL만) | 없음 — 격리 월드에서 표준 API 구독 | **권장** |
| B. MAIN 월드 fetch/XHR 패치 | 있음 | 높음 — 페이지 주입, 사이트 갱신·CSP에 취약 | 보류 |
| C. chrome.webRequest (background) | 없음 | 낮음, 단 background→content 메시지 왕복 지연 추가 | A 실패 시 폴백 |
| D. chrome.debugger | 있음 | 디버깅 배너·과도한 권한 | 제외 |

A를 권장하는 근거: 감지에 필요한 것은 "응답이 도착했다 → 지금 스캔하라"는 **신호**뿐이다. 슬롯 클릭은 어차피 DOM 렌더를 기다려야 하므로, 바디를 파싱해 슬롯을 먼저 알아내도 이득이 렌더 지연(R3)만큼으로 제한된다. 신호만 쓰면 자동화 경계도 불변(관측만 추가, 클릭 대상·한계 변화 없음).

### 아키텍처

```
SlotRefreshWatchPort {
  start(onArrival: (arrivalAt: number) => void): void;  // URL 필터는 어댑터 내부 상수(R1 실측값)
  stop(): void;
}
```

- 어댑터 계층에 PerformanceObserver 구현(`src/content/adapter/slot-refresh-watch.ts`). 필터 미스면 콜백이 안 울릴 뿐 — 실패 모드가 무해.
- 오케스트레이터 통합: 토글 클릭 루프(자극)는 유지. 감지를 이벤트 융합으로 확장:
  1. **도착 신호 수신 시**: 목표 날짜 선택 상태 확인 후 즉시 스캔 버스트(예: 10ms 간격, 상한은 R3 실측 렌더 지연 + 여유). 블라인드 구간(인접 날짜 표시 중)에 신호가 오면 목표 재클릭 직후로 버스트를 이연.
  2. **기존 사이클-말 스캔은 폴백으로 유지**: 신호가 안 오는 환경(URL 패턴 변경, API 미지원)에서도 현행 동작 그대로.
- 계측: `xhrArrivalServerAtMs`·`arrivalToDetectMs`를 SLOT_DETECTED data에 추가 — 개선 폭을 실런에서 직접 검증.

### 성능·안전 불변식

- Observer 콜백은 필터 매치 시에만 실행 — 핫패스 오버헤드 무시 가능. 버스트 스캔은 상한이 있어 CPU 폭주 없음.
- 자동화 경계 스펙 불변. 관측 계층 추가일 뿐 클릭 정책 변화 없음.
- R2 결과에 따라 인접 토글 폐기가 가능해지면(같은 날짜 재클릭으로 재요청 유발 시) 블라인드 구간 자체가 사라진다 — 별도 후속 스펙으로 분리.

## 4. 구현 계획 (TDD, 단계별 커밋)

1. **정찰(R1~R5)** → site-behavior.md 새 절 + 이 스펙의 상수 확정. *(게이트)*
2. `slot-refresh-watch.ts` 어댑터 + 단위 테스트(fake PerformanceObserver로 필터·start/stop·콜백 검증).
3. 오케스트레이터 이벤트 융합 + 폴백 유지 — 기존 fake-clock 하네스 확장(도착 신호 주입 → 감지 시각 단축 단언, 신호 없음 → 현행 경로 회귀 단언).
4. 계측 필드 추가 + trace-view 표시(필요시).
5. 실런 검증: openDelta 분포 비교. 성공 기준: 감지 ≈ 도착+렌더(오픈런 기준 +250ms 이하), 폴백 경로 회귀 없음.

## 5. 리스크

- **신호 누락**(사이트가 URL 패턴 변경): 폴백 스캔이 그대로 살아 있어 현행 수준 유지 — 성능 회귀 없음.
- **렌더 전 버스트 낭비**: 상한으로 제한, R3 실측으로 튜닝.
- **전송 방식 변경**(fetch→WebSocket 등): 방식 A 무력화되나 폴백으로 동작 유지, 그때 방식 C 재평가.
