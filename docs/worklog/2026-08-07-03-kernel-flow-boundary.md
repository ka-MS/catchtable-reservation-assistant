# 2026-08-07-03 커널·흐름 경계 (SP-025/02)

## 한 것

- SP-025 02 착수 전 재평가를 수행하고 결과를 설계에 기록했다. 01의 전제는
  유지된다.
- `RunSession`을 `RunKernel`(안전 계약)과 `RunSession`(오픈런 흐름)으로
  갈랐다. 흐름은 `RunFlowHooks`의 `start`/`steps`/`cleanup`으로 끼운다.
- 생명주기 순서 특성화 테스트를 **추출 전에** 작성했다.
- HANDOFF의 진행 중 브랜치와 검증 기준(540/540 → 622/622) 갱신.

## 내린 결정

**`confirmPageReady`는 흐름으로 보냈다.** 00-index가 02에 미뤄 둔 미결
항목이다. 인접 가용 날짜는 날짜 토글의 왕복 대상이라 오픈런 전용이고,
다른 흐름에 적용하면 근거 없이 실패한다.

**커널을 별도 파일로 빼지 않았다.** `tests/build-regression.test.mjs`가
`dist/content/orchestrator.js`의 소스 텍스트로 PIN 폐기 순서를 검사한다.
파일을 옮기면 그 테스트가 깨진다. 00-index의 중단 조건은 기존 테스트 수정을
"경계를 잘못 그었다는 신호"로 본다. 이 단계에 필요한 것은 클래스 경계이지
파일 경계가 아니므로 초안을 철회했다.

**흐름이 커널 terminal API를 42회 호출하는 것은 줄이지 않았다.** 결합이
아니라 의도된 방향이다. `this.kernel.` 접두사를 붙여 소유권이 호출부마다
보이게만 했다.

## 검토했다 버린 선택지

- **상속으로 커널을 공유** — 코드베이스에 클래스 상속 0건이고 사용자가
  컴포지션을 명시했다.
- **흐름 컨텍스트 인터페이스를 지금 정의** — 구현체가 하나뿐인 상태에서
  정하면 오픈런 전용 개념이 들어간다. 04 몫이며 게이트가 걸려 있다.
- **cleanup 예외 처리 개선** — `slotWatch.stop()`이 던지면 flush가 건너뛰어진다.
  바람직하지 않지만 이 단계는 동작 무변경이다. 고치는 대신 테스트로 고정했다.
- **흐름 본문을 손으로 옮기기** — 719줄이라 조용한 누락이 생긴다. 원본 줄
  구간을 재조립하는 일회용 스크립트를 썼다.

## 남은 것

- **Chrome 오픈런 dry-run 1회(성공 기준 5) 미확인.** 병합 전 필요 여부는
  사용자 판단이다.
- 03 핫패스 전략 추출. 대상은 `RunSession`에 남은 핫패스와 흐름 상태
  8개이며, 범위는 02 결과 재측정으로 확정한다.

## 배운 것

손으로 적은 기대값이 두 곳 틀렸고 **추출 전** 실행이 그걸 잡았다. terminal
상태와 `referenceClock.stop`의 위치다. 추출 후에 테스트를 썼다면 틀린 순서를
정답으로 굳혔을 것이다. 01에서 세운 "덤프해서 붙여넣는다"가 두 번째로
효과를 봤다.

구간 자르기 스크립트가 다음 메서드의 jsdoc을 반토막 내 블록 주석이 닫히지
않았다. `tsc`는 이걸 실제 원인보다 40줄 아래의 클래스 선언 오류로 보고했다.
스크립트에 구간별 주석 균형 검사를 넣어 다음엔 구간 이름으로 실패하게 했다.
