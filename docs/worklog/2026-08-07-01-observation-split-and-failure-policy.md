# 관측 분리와 실패 정책

**날짜:** 2026-08-07
**세션:** SP-025/01, SP-026
**PR:** [#19](https://github.com/ka-MS/catchtable-reservation-assistant/pull/19) spec ·

[#22](https://github.com/ka-MS/catchtable-reservation-assistant/pull/22) 실패 정책
**이슈:** [#20](https://github.com/ka-MS/catchtable-reservation-assistant/issues/20) (해소)

## 한 것

- 웨이팅·줄서기를 추가하면 기존 코드를 얼마나 건드리는지 묻는 질문에서
  시작했다. 감으로 답하지 않고 구조를 측정했다.
- 측정 결과 **과설계가 아니라 과소설계**로 판정했다. 클래스 상속 0건,
  파일 중앙값 82줄, 흐름 종속 코드 35.6%. 문제는 `orchestrator.ts`의
  제어·관측 혼재였다.
- SP-025로 4단계 계획을 세우고 `01` 관측 분리를 완료·병합했다.
  `orchestrator.ts` 1,630 → 1,190줄.
- `01` 작업 중 관측 예외 격리가 비대칭임을 발견해 #20으로 분리했고,
  SP-026으로 해소했다.

## 결정

| 결정 | 근거 |
|---|---|
| 장기 브랜치 대신 순차 브랜치 | 각 단계의 중간 상태가 전부 배포 가능해 격리 이득이 없다 |
| `03`을 `03`(추출)/`04`(일반화)로 분리 | 추출은 오픈런 코드만으로 결정 가능. 일반화만 두 번째 흐름이 필요하다 |
| `01`에서 격리 비대칭을 보존 | 동작 무변경 범위를 지켜야 회귀 시 원인을 분리할 수 있다 |
| 관측 실패는 전부 격리하고 카운트로 드러낸다 | 관측은 부수적이나, 조용히 삼키면 진단이 죽은 것을 아무도 모른다 |
| 검증 수치는 한 문서만 보유 | 같은 값을 여러 곳에 적으면 반드시 어긋난다. 이 PR에서만 세 번 어긋났다 |

## 검토했다 버린 것

- **상위 장기 브랜치 + 하위 브랜치** — 중간 상태가 배포 가능해 격리
  이득이 없고 `orchestrator.ts` 드리프트 비용만 남는다.
- **`IOrchestrator` 인터페이스화** — 커널을 흐름마다 복제하면 안전 계약
  (PIN 폐기 순서, cleanup 순서)도 복제된다. 흐름 정의를 주입하는 쪽으로.
- **격리 비대칭을 "의도된 것"으로 문서화** — 각 지점이 왜 다른지 설명할
  근거가 없다. 정당화 못 하는 비대칭을 굳히면 그 문서가 부채가 된다.
- **공통지침 허브 문서 신설** — 자동 로드가 안 돼 홉만 늘어난다.
  `AGENTS.md`에 표로 넣는 쪽이 낫다.

## 남은 것

- SP-025 `02` 커널·흐름 경계 (다음 단계)
- SP-026 한계 3건 — `finally` 단계 실패 미집계, `emit` 지속 실패 시
  카운트 유실, 실패 원인 미기록
- 새 예약 흐름(웨이팅·줄서기)은 실측 근거가 없어 착수 불가

## 실수

**검사 축을 하나만 보는 실수를 세 번 반복했고 전부 리뷰가 잡았다.**

| 본 축 | 놓친 축 |
|---|---|
| `catch` 개수 | 경계의 범위 (`sendSafe` 인자 평가) |
| A(격리)의 효과 | B(카운터)의 payload 효과 |
| `serverAt` 실패 | `state` 실패 (`failureData`) |

문서 서술 오류도 다섯 건 있었다. 전부 "데이터는 맞는데 요약 문장이
틀린" 형태였고, 요약이 깔끔할수록(`64%`, `0`, `1`, "없다") 틀렸다.

HANDOFF 정합성은 세 번 놓쳤다. 수치 중복이 원인이라 판단해 규칙을
세우는 대신 **적을 자리를 하나로 줄였다.**
