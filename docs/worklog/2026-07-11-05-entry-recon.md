# 2026-07-11 예약창 진입 실측 작업 로그

## 목적

네비게이션 파이프라인(URL 이동 → 예약창 진입 → 날짜 선택 → 실행 모드) 설계의 근거 확보. 진입 흐름이 가게마다 다를 수 있다는 전제로 유형이 다른 매장 3곳을 교차 실측했다.

## 방법

`.claude/skills/catchtable-recon` 워크플로 A를 처음 실전 적용했다. 페이지에 `history.pushState/replaceState` 후킹과 MutationObserver(날짜 셀 출현 타임스탬프)를 주입한 뒤 `예약하기` CTA를 클릭해 전환을 계측했다. 전역 계측 객체의 생존 여부로 풀 리로드를 판별했다.

## 결과 (상세는 `docs/analysis/site-behavior.md` §1.1)

- 진입은 완전 SPA: `aside#dock`의 `예약하기` 클릭 → `replaceState`(+`date=YYMMDD`) → 같은 문서에 달력 모달. 풀 리로드 없음.
- 달력 셀 렌더 287~350ms. 진입 판정은 관측 폴링 기반이어야 함.
- 인원 칩은 달력과 같은 모달(기본 2명 선택). 달력 선행 단계 아님.
- 가게별 변형: 돗가비누각 모달에 테이블 타입 필터 드롭다운, 매진 날짜엔 `빈자리 알림 신청` 버튼.
- 웨이팅 전용 매장(런던베이글뮤지엄 안국)은 `예약하기` 부재 + disabled `현장 웨이팅만 가능` — 진입 단계의 안전 실패 판별 근거.

설계 함의: 페이지 이동은 background 세션 층, 진입·날짜 선택은 content 층에 두는 2층 구조가 성립한다(진입 이후 전 과정이 같은 문서). `enter_reservation` 단계의 성공 조건은 날짜 셀 관측, 실패 조건은 `예약하기` 부재(웨이팅 전용 등)다.

## 안전 준수

예약 확정·결제·웨이팅 등록·알림 신청 버튼은 클릭하지 않았다. 클릭한 것은 검색 UI, 매장 이동, `예약하기`, `닫기`뿐이다.

## 스킬 검증 (GREEN)

워크플로 A 절차는 유효했고, 실전에서 결함 2건을 발견해 스킬에 보강했다.

1. 좌표 측정과 클릭 사이 리렌더로 오클릭 2회 발생 → 클릭 직전 재확인 규칙 추가.
2. javascript_tool 반환값에 URL 쿼리스트링이 포함되면 도구가 차단함 → pathname만 반환 규칙 추가.
